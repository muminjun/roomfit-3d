## 0. 임무 (읽고 바로 실행)

너는 React·TypeScript·Konva CAD형 편집기·2D 계산기하·Three.js/R3F·QA·GitHub Pages를 구현할 수 있는 시니어 엔지니어다. **실측 기반 2D·3D 인테리어 웹앱 RoomFit 3D를 MVP 전체(S0~S5)까지 실제로 구현·검증하라.** 단일 공간, 한 층, 직각 경계, 가구 20종, 실측 mm, 2D→진짜 3D, Undo/Redo, 로컬 저장/JSON, GitHub Pages가 **전부 P0**다. 설명이나 계획만 출력하고 멈추면 실패다. 이 파일을 읽은 직후 작업 폴더를 점검하고 S0 파일 생성을 시작하라.

최종 사용자 여정(최상위 성공 기준): `새 방 4200×3400×2400mm → 벽 이동 → 홈/돌출·ㄱ/ㄷ → 20종 카탈로그 DnD·클릭 추가 → 가구 위치·W/D/H·90° 변경 → 오목 방 및 가구 충돌 확인·복구 → 실제 3D OrbitControls → Undo/Redo·자동저장·JSON 백업 → Pages 하위경로 정상 실행`.

**정확성 > 전체 사용자 여정 완주 > 데이터 보존/오류 처리 > 3D 동기화/성능 > 디자인 장식.** UI용 mock 숫자·정적 3D 카드·실제로 작동하지 않는 버튼을 구현으로 보고하지 말 것.

## 2. 실행 프로토콜

### 2.1 시작 (재개 포함)

1. 터미널 사용 가능 여부와 현재 디렉터리가 기존 저장소인지 `pwd`, `ls`, `git status --short --branch`, `package.json`, `src/`, `.github/`를 먼저 확인한다. `PROGRESS.md`, `TEST_REPORT.md`, `DECISIONS.md`가 있으면 먼저 읽는다. **`PROGRESS.md`(또는 기존 `IMPLEMENTATION_STATUS.md`)가 있으면 새로 시작하지 말고 거기 기록된 단계·미완료 항목부터 이어서** 진행한다. 이미 구현된 코드는 재사용하고 PRD와의 기능 차이만 구현한다. 사용자 미커밋 변경·기존 git 이력을 절대 삭제/reset/force-push하지 않는다. 기존 저장소면 새 브랜치 `feat/roomfit-mvp`에서 작업한다.
2. 빈 폴더면 React + TypeScript(strict) + Vite(react-ts 템플릿) 프로젝트를 만들고 즉시 실행한다. 기존 프로젝트라면 기존 package script·Node/TS/R3F 호환 범위·현재 빌드 상태를 확인한다.
3. 패키지 설치 시 `npm view <pkg> version peerDependencies engines`로 호환을 확인하고 lockfile을 커밋한다. React 19 ↔ @react-three/fiber 9.x ↔ @react-three/drei 10.x ↔ react-konva 19.x는 **peerDependencies로 직접 확인**한다(이 프롬프트 작성 시 외부 검증은 일부 미완료). `@react-three/fiber` v10 알파 등 미검증 prerelease·알파·베타 금지.
4. 지시문만 읽고 과거 코드가 있다고 가정하지 않는다. 사용자 GitHub 계정/레포를 모르면 지어내지 말고 기본 프로젝트 이름 `roomfit-3d`를 임시 값으로 쓰되 실제 배포 단계에서는 설정된 저장소명에서 base를 파생한다. 권한 없는 원격 push·Pages 설정은 수행했다고 주장하지 않는다.
5. 사용자의 기존 JSON/localStorage 프로젝트를 파기하지 않는다. 파일 import, new project, example replace는 이전 프로젝트 백업 또는 확인 후 원자적으로 변경한다.
6. 3~6줄짜리 작업표(`현 저장소 상황 / P0 누락 목록 / 주요 폴더 / 데이터 모델 / S0~S5 체크리스트`)를 `PROGRESS.md`에 쓰고 **즉시** 코드를 만든다. 질문으로 멈추지 않는다(작은 모호함은 안전한 기본값을 골라 `DECISIONS.md`에 기록). 데이터 손실·원격 파괴·비용·비밀키 노출 위험이 있는 일만 사용자 확인을 받는다.

### 2.4 검증 명령과 npm 스크립트 (실제 실행한 것만 보고)

`npm ci` → `npm run typecheck`(= `tsc -b`) → `npm run lint` → `npm run test`(vitest, `tests/e2e` 제외) → `npm run build` → 가능하면 `npm run test:e2e`. 실패하면 원인을 수정하고 **같은 명령을 다시 실행**한다. 같은 수정이 두 번 실패하면 다른 가설로 전환하고 `DECISIONS.md`에 적는다. 브라우저 바이너리가 없어 E2E를 못 돌리면 `미검증`과 사유를 기록하고 수동 점검 절차를 남긴다. Playwright 브라우저 설치도 포함해 사용 가능한 E2E는 수행한다.

`package.json`에는 최소 다음과 **실제로 동작하는** scripts를 둔다(템플릿에 맞춰 조정 가능).

```json
{
  "scripts": {
    "dev": "vite",
    "typecheck": "tsc -b",
    "lint": "eslint .",
    "test": "vitest run",
    "test:watch": "vitest",
    "test:e2e": "playwright test",
    "build": "tsc -b && vite build",
    "preview": "vite preview"
  }
}
```

Vite 템플릿의 `tsconfig.json`이 project references만 담으면 `tsc --noEmit`은 실 코드를 검사하지 않고 성공할 수 있다. `tsc -b`가 소스 오류를 실제 검출하도록 만들고, 설정 직후 임시 고의 타입 오류를 격리 테스트로 넣어 typecheck가 실제 실패함을 확인한 다음 즉시 제거한다(AC-78). `vitest` 설정에 `exclude: ['tests/e2e/**']`를 넣어 Playwright 파일이 단위 테스트로 실행되지 않게 한다. 검사 불가 환경은 `통과`가 아니라 `미실행/환경상 불가`로 기록한다.

## 3. 필수 아키텍처 계약 (아래 PRD 전문이 상세 정의)

- 영속 구조의 원본은 `ProjectDataV2{schemaVersion:2,unit:'mm',room,furniture,settings}` 단일 Zustand store. 방 꼭짓점·W/D/H·벽 두께는 mm **정수**, 가구 중심 `position.x/y`는 **0.5mm 배수**(§3.1), 3D는 mm→m 변환. UI ghost/selection/viewport/history/derived warnings는 별도.
- 폴리곤은 오직 닫힌 **직각 단순 다각형**이며 첫 꼭짓점 중복 금지. `nIn=(-dy/L,dx/L)`, `nOut=(dy/L,-dx/L)`는 y-down 2D 모델 기준. `offset>0`은 바깥쪽. 홈은 `[A,S,S+n*d,E+n*d,E,B]`. 정규화·ID 매핑·교차·최소벽 검사를 통과한 변경만 원자적으로 기록한다. 모든 id는 주입 가능한 `IdGenerator` 한 곳에서 만든다(§8.5).
- 오목 방에서 꼭짓점 4개만으로 가구 포함 검사 금지: polygon x/y 경계에 따른 열린 셀 midpoint 테스트. 두 가구는 x/y에서 **양의 면적**으로 겹칠 때만 차단; 접촉 허용. 높이 검증과 기존 invalid 가구 복구 경로 포함. 스냅은 footprint 좌상단 기준이며 홀수 W/D도 중심이 0.5mm 배수라 격자·벽에 정확히 접한다.
- 2D 모델 `(x,y)`는 3D `(x/1000,0,y/1000)`에 대응. 2D 화면 시계방향 +90° 회전은 3D Y축 yaw `-π/2`. 바닥은 FR-030 확정 레시피(`Shape(x/1000, −y/1000)`→`ShapeGeometry`→`rotateX(−π/2)`)로 만들고 법선이 +Y인지 테스트한다. 단순 벽 박스 겹침에 의한 z-fighting을 방치하지 말고 외벽 셀 합집합/측면 경계 메쉬(FR-033)를 구성한다.
- 모든 명령은 `candidate → validate → commit/NoChange/Invalid → one history entry → autosave debounce`; preview는 데이터 아님. 방/높이를 줄일 때 이전 가구 무효는 **경고 파생**, 새 가구의 무효 배치는 거부. Undo/Redo/JSON/localStorage/2D/3D의 원본이 일치해야 한다.
- DnD는 DOM `dragstart` catalogId를 참조하고 `dragover.preventDefault`, `clientX/Y−stageRect`와 줌·팬 역변환, **같은** placement validator로 drop 검사. Stage 이탈·Esc·도구 변경 시 cancel. 터치/키보드는 카탈로그 클릭 추가/속성 수치편집 제공.
- localStorage 손상 데이터 보존, `QuotaExceededError`/SecurityError 처리, JSON 2MiB 제한·strict schema·중복 ID 거절·원자적 import, 다중 탭 저장 일시중지와 경고. 저장 불가능할 때 수동 JSON 백업.
- `src/lib/geometry`, store/command, editor2d, viewer3d, tests를 각기 별도 모듈로 분리하며(PRD §13 폴더 구조) 하나의 거대한 컴포넌트로 만들지 않는다. **한 번에 파일 몇 개씩** 만들고 매번 검증한다.

## 4. 반드시 피할 실패 (이 목록 항목이 보이면 즉시 수정)

- 랜딩/껍데기 UI만 만들고 편집기·충돌 엔진을 뒤로 미루기. 지금 단계 코드를 안 쓰고 계획만 늘어놓기.
- 3D를 이미지·CSS·가짜 모형으로 대체하거나 2D와 별도 데이터를 갖게 하기. 단일 store가 유일한 원본이다.
- 가구 네 모서리만으로 오목 방 포함 판정(UT-PLC-01/02가 이를 잡는다).
- 방 수정 시 가구를 몰래 삭제/이동. 무효 가구는 경고만.
- 화면 px를 모델에 저장, 3D에서 mm→m 누락, 가구 중심을 정수로 강제(0.5mm 배수여야 함), 폴리곤 꼭짓점에 소수 저장.
- 비어 있는 `onClick`, 하드코딩된 성공 표시, 구현 안 된 기능 버튼.
- 거대한 단일 컴포넌트/한 번에 전체 생성.
- 테스트를 실행하지 않고 "통과"라고 보고, `any`/`@ts-ignore`로 오류 은폐. 중요한 AC를 fake pass로 만들기. 미설치 브라우저와 원격 Pages를 로컬 빌드 통과로 대체하기.
- 단위 테스트 고정값을 임의로 바꾸기. 샘플 방 **14.28㎡**, 800×500 함몰 **13.88㎡**, 같은 크기 돌출 **14.68㎡**, 1000×600 돌출 **14.88㎡**, L형 **12.36㎡**, U형 **13.08㎡**, 상단 벽 바깥 +200 **15.12㎡**, 오른쪽 벽 바깥 +150 **14.79㎡**, 퀸 침대 90° footprint **2000×1500mm**는 공식 구조대로 실제 계산되어야 하며, 상이한 두 돌출 크기를 같은 사례라고 말하지 않는다.
- 원격 권한 없이 "배포했다"고 보고. push·Pages 활성화·URL 접속 확인을 **실제로 했을 때만** "배포 확인 완료". 아니면 "로컬 빌드 + 배포 파일 준비 완료, 원격 미검증".
- `/assets` 절대 경로, 비밀키·개인정보 커밋, 오류 시 사용자 autosave 덮어쓰기.
- 확장 기능(문·창문·여러 방·GLB·협업 등)을 MVP에 섞기. 범위 밖이다.

## 5. 보고 형식

각 단계 종료: ① 체험 가능한 기능 ② 실제 변경 파일 ③ 실제 실행한 명령과 종료 코드(성공/실패/미실행) ④ AC 통과/실패/미검증 ⑤ 알려진 제약·위험·다음 단계. 최종 답변에는 상태(MVP 전체 완료/부분 완료/배포 준비 완료/원격 배포 확인 완료 중 해당), 복사 가능한 로컬 명령, 14.28→13.88→14.68→14.88㎡·ㄱ 12.36·ㄷ 13.08 및 퀸 침대 90° 2000×1500 테스트의 **실제 결과**, 미검증 항목을 정직하게 쓴다. 모든 S0~S5가 목표지만 환경·권한으로 불가능하면 그 지점까지 **실제 가능한 작업을 최대한 실행하고** `PROGRESS.md`에 남은 단계를 적으며 완료로 표시하지 않는다. 사용자에게 매 단계 불필요한 승인을 요구하지 않는다(데이터 파기·원격 push·비용은 예외).

- 중요한 조작마다 1~2문장 툴팁, 빈 상태 및 실패 원인을 표시.

## 3. 수치·좌표·데이터 계약 (모든 구현의 기준)

### 3.1 저장 단위 및 방향
1. **[v3]** 방 꼭짓점·모든 W/D/H·벽 두께는 **mm 정수**. **가구 중심 `position.x/y`는 0.5mm의 배수**(홀수 W/D 가구가 벽·격자에 정확히 접하게 하기 위함; 0.5는 IEEE754에서 정확 표현). 임시 계산은 소수 허용; 커밋 때 정수 항목은 `Math.round`, 가구 중심은 `Math.round(v*2)/2`로 정규화(회전각은 0/90/180/270). 저장 JSON의 가구 중심이 0.5 배수가 아니면 거부.
2. 2D 모델 좌표: **x 증가 = 오른쪽**, **y 증가 = 아래쪽**. 기본 방 꼭짓점: `(0,0) → (4200,0) → (4200,3400) → (0,3400)`.
3. 꼭짓점 배열은 첫점을 끝에 중복하지 않는다. 위 순서를 ‘**화면에서 시계 방향, shoelace signed area > 0**’의 정규 방향으로 정의한다.
4. 화면 좌표(y 아래 증가)의 진행 방향 기준 **시각적 오른쪽**이 실내다. `t=(dx/L,dy/L)`이고 **내부 법선 `nIn=(-t.y,t.x)`**, **외부 법선 `nOut=(t.y,-t.x)`**. 상단 A=(0,0)→B=(4200,0)이면 `nIn=(0,+1)`, `nOut=(0,-1)`이다. 수학적 y-상향 좌표계의 왼쪽/오른쪽 법선과 용어를 혼동하지 않는다.
5. 3D 변환: `(x2d,y2d)` → `(x3d=x2d/1000, Y3d=높이Mm/1000, z3d=y2d/1000)`. 3D y가 높이축이며 1 unit=1m. 2D 화면에서 시계방향 +90°인 가구 회전은 Three.js의 **Y축 회전 −π/2**와 대응한다. 2D polygon을 `(x,0,z)`에 그대로 올려 삼각분할하면 법선이 −Y가 될 수 있으므로 바닥은 FR-030의 확정 레시피로 만들고 +Y 법선을 테스트로 확인한다(§9).
6. Konva 편집 영역의 CSS 화면 좌표: `screenX=worldX*zoom+panX`, `screenY=worldY*zoom+panY`, 역변환 `(screen-pan)/zoom`. `zoom` 단위는 CSS px/mm. DOM `clientX/Y`에서 Stage 컨테이너 `getBoundingClientRect().left/top`을 먼저 빼며 DPR은 직접 곱하지 않는다. Stage 자체에 추가 변환 계층이 있으면 `getAbsoluteTransform().copy().invert()`를 단일 변환 경로로 사용한다. 화면 픽셀은 영속 모델에 저장하지 않는다.
7. 카메라 줌/팬, 활성 도구·선택 대상은 UI 상태; 방 polygon·가구 좌표/치수는 영속 프로젝트 상태. 2D와 3D는 동일 store 데이터를 읽는다.

- 폴리곤 면적은 shoelace 공식으로 **mm²**를 구한 후 `1_000_000`으로 나누어 ㎡ 표시. 구조 편집 시 합법적인 도형만 커밋한다.
- 위 수치는 구현 결정을 위한 MVP 기본값이며 상수 파일(`src/config/limits.ts`)에서 관리한다.

### 3.3 직각 다각형 유효성 및 정규화(필수 순서)

1. **모델과 파일 모두 꼭짓점 배열은 개방형**이며, 마지막 점에 첫 점을 다시 넣지 않는다. 각 `{id,x,y}`의 id는 전역 polygon 내 고유·비어 있지 않은 문자열이며 좌표는 mm 안전 정수다. 꼭짓점 수 4~64, 짝수 개, 각 좌표의 절댓값 ≤30,000, bbox 가로/깊이 각각 500~30,000이다.
2. 순수 함수 `normalizeEditCandidate(input, previous, selectedEdgeId)`는 편집 후보의 연속 중복점/0길이 변과 **정확히** 같은 직선 위의 중간점을 정리하고, `oldId→survivingId` 매핑 및 `selectedEdgeId` 재연결 결과를 돌려준다. 앞 변의 시작점 ID를 우선 유지하되 같은 좌표의 기존 ID를 우선한다. 중복된 새 ID는 생성 자체가 오류다. 정규화 후 100mm 미만이지만 0이 아닌 변은 제거하지 않고 거부한다. 이 함수를 드래그 프리뷰와 커밋에 공통 사용한다. 벽을 이웃 벽과 같은 선에 맞춰 홈이 사라지는 편집(예: 함몰 안쪽 벽을 원래 벽 위치까지 되돌림)은 거절이 아니라 **정상 병합**이며, 병합된 변은 앞 변의 시작 vertex id를 유지하고 제거된 id를 가리키던 선택은 병합된 변으로 옮긴다.
3. `validateRoomPolygon(normalized)`는 (a) 꼭짓점/ID/범위/짝수 검사 (b) 수평·수직 변(양 좌표 중 정확히 하나만 변경), 각 변 ≥100mm (c) 전역 중복점 금지 (d) 비인접 선분의 교차·겹침·끝점 접촉·T자 접촉 금지 (e) 인접 변의 무의미한 일직선 연결 없음 (f) shoelace 면적 양수, 0 아님을 확인한다. 뒤집힌 단순 입력은 전체 순서를 뒤집되 **정규화 함수가 명시된 경로에서만** 수행하고 ID는 점을 따라 보존한다. 기하 검사는 부동소수 EPS가 아닌 정수 방향성과 선분 범위 비교를 쓴다. 편집 중 내·외부가 뒤집히는(면적 부호가 바뀌는) 후보는 거절한다.
4. **외부 JSON은 편집 후보가 아니다.** 지원 스키마 파싱·중복 ID/중복점/비정상 좌표/교차를 먼저 거부한다. **[v3]** 반시계(shoelace<0) 방향 polygon은 거부하지 않고 뒤집어 정규 방향으로 정규화한 뒤 검증한다(vertex id 보존, §8.5). 방향 반전 및 일직선 중간점 정규화로 원본이 바뀌는 경우 변경 내역을 사용자에게 표시하고 교체 전 확인한다. 원본 프로젝트와 자동 저장은 확정 전 불변. 망가진 JSON을 "정규화했으니 정상"으로 묵인하지 않는다.
5. 폴리곤에는 구멍이 없다. ㄱ자/L형은 코너 제거 프리셋, ㄷ자/U형은 중간 홈 형태이며 홀(hole) 데이터가 아니다. 음수 좌표는 합법적이다. 면적은 `sum(x_i*y_{i+1}-x_{i+1}*y_i)/2` mm²로 구하고 ㎡는 1,000,000으로 나눈 표시값일 뿐 모델에 저장하지 않는다.
6. 유효성 실패는 `{ok:false, code, message, offenderIds}`를 반환한다. 편집 거부 시 마지막 정상 프로젝트·Undo·autosave를 변경하지 않는다. 편집 명령이 실제로 아무것도 바꾸지 않았다면 히스토리를 추가하지 않는다.
7. 다각형 정규화 함수는 입력을 직접 변형하지 않고 새 배열을 반환하며, 뷰 모델이 원본을 오염시키지 않게 한다.

### 3.4 원자적 편집과 검증의 공통 파이프라인

```text
DOM 입력/키/드래그 → parse(입력 중간값은 UI에만 보관)
→ validated mm candidate (snap은 드래그에만 적용)
→ normalizeEditCandidate (방이면) → validateRoomPolygon
→ validatePlacement (가구 이동/추가/크기/회전이면)
→ 성공: committed ProjectData 갱신 1회 → derived selectors 갱신
          → history 1건 → autosave debounce 재예약
  실패: preview ghost+사유만 표시 → Esc/드롭 시 이전 상태 유지
```

- 편집 불변식은 **구조와 새 가구 배치**를 구별한다. 이미 존재하던 가구는 벽 변경으로 무효가 될 수 있으며 **삭제·자동 이동 금지, 경고만 파생**한다. 구조적 무효 polygon은 어떤 경우에도 커밋하지 않는다.
- `NoChange`, `Invalid`, `Committed`를 구분해 호출자가 토스트와 히스토리를 일관되게 처리한다. 에러 예외를 무조건 삼키지 않는다.
- `PointMm.id`는 2D 선분 키이자 히스토리·UI 선택 참조다. 위상 변경 후 사라진 id는 가장 가까운 동일 직선의 살아있는 변으로 매핑되거나 선택 해제한다. 이름/색상/크기/좌표의 저장 규칙은 §10·11을 따른다.

### 3.5 좌표·정밀도 역변환의 검증용 예제

- `zoom=0.5 CSS px/mm`, `pan=(100,50) CSS px`, `client=(500,350) CSS px`, 컨테이너 좌상단 `(20,30) CSS px` → local `(480,320)` → world `(760,540)` mm. 반대로 world `(1000,2000)`은 screen `(600,1050)`이다(UT-VIEW-01). 스냅이 꺼져 있으면 벽은 mm 정수, 가구 중심은 0.5mm 배수로 저장된다.
- 포인터 중심 확대: 확대 전 `q=(pointer-pan)/zoom`; 변경 배율 `zoom'`에서 `pan'=pointer - q*zoom'`로 구해 포인터 아래 실측점을 보존한다. `pan`은 로컬 컨테이너 좌표계다. 줌 인 100회→아웃 100회 뒤에도 포인터 아래 world 좌표 오차는 `1e-6` 미만이고 저장 데이터는 불변이다(UT-VIEW-02).
- 홀수 폭 예제 [v3]: 폭 `1001mm` 가구의 왼쪽 모서리를 `x=100mm` 격자에 **정확히** 맞추면 중심은 `600.5mm`이며, 이는 0.5mm 배수라 합법이다. 스냅은 footprint 좌상단 `(minX,minY)`를 격자에 맞춘 뒤 `중심 = snappedMin + worldW/2`로 계산하므로 홀수·짝수 모두 가장자리가 격자·벽에 정확히 일치한다(짝수 폭 1000mm, 목표 minX=100mm → 중심 600mm). 숫자 입력은 스냅하지 않으며 입력된 중심이 0.5mm 배수가 아니면 거부한다.
- 2D 시계방향 90° 회전은 3D `rotation.y=-Math.PI/2`, 180°는 `-Math.PI` (동일한 X/Z 크기여도 방향 표식은 보존). 드래그·회전·카메라 줌은 세계 mm를 바꾸지 않는다.

## 4. 프로젝트 생성·사각방 편집

### FR-001 — 새 프로젝트
- 기본값 `가로 4200 / 세로 3400 / 높이 2400 / 벽두께 120 (mm)`.
- 빈 값, 0, 음수, 소수, 과도한 수치와 `NaN`, `Infinity`는 즉시 구체적으로 표시.
- 유효 값으로 방을 생성하면 2D 뷰를 자동 맞춤하고, 3D 카메라의 초기 타깃도 데이터로 계산.
- 현재 편집 내용이 존재할 때 `새 프로젝트`, `예제 열기`, `JSON 불러오기`로 덮어쓰기 전 확인(내보내기 안내 포함).
- 사각 방 생성 시 polygon 꼭짓점은 `(0,0),(W,0),(W,D),(0,D)`이며, 방 높이·벽 두께는 별도 속성.

### FR-002 — 사각형 크기 수정
- 사각 방(꼭짓점 4개, 모든 변 수평/수직)은 우측 패널에서 가로/세로 숫자로 수정 가능. **bbox 좌상단 `(minX,minY)` 고정**, 오른쪽/아래쪽 끝 변이 따라 움직이는 **앵커 정책**. 상단 벽을 밖으로 옮겨 좌상단이 `(0,-200)`이 된 뒤에도 같은 규칙이다(좌표 `(0,0)`을 하드코딩하지 않는다).
- 사각형일 때 각 벽을 선택해 그 벽의 법선 방향으로 끌어 정확한 크기 변경 가능.
- **오목/복잡한 방에서는 ‘전체 bbox 너비·깊이’는 읽기 전용**. 무리하게 전체 비례 확대하지 않는다. 대신 개별 벽 이동 및 높이/두께 수정으로 조정.
- 사용자에게 전체 너비·깊이는 bbox 치수임을 명시하고, 독립 벽 길이와 혼동하지 않게 한다.

### FR-003 — 일반 벽 세그먼트 이동
- 방의 **연결된 한 변**을 선택, 벽에 **수직인 방향으로만** 드래그한다. 자유 이동·비직각 변은 허용 안 함.
- 수평 변은 두 끝점의 y만 함께 변경; 수직 변은 두 끝점의 x만 함께 변경한다. 다른 꼭짓점은 그대로 두어 인접 벽의 연결 상태를 유지한다.
- 벽 이동이 일으키는 최소 길이·자가 교차·면적·bbox 규칙 위반은 미리보기 빨강 + 사유 → 드롭 시 취소. 유효 후보만 단일 커밋한다. **드래그 시작점의 스냅 오프셋**, 현재 변의 수직 단위 법선, 커밋 전 정수 mm 정규화 순서를 고정한다.
- 선택 벽 속성에 읽기용 `현재 길이`, 현재 좌표, 법선 수치 이동 `+/- N mm` 입력 제공; 수치 편집은 스냅을 강제로 적용하지 않는다.
- **벽 이동은 위치 변경이지 해당 벽 길이만 늘리는 동작이 아님**을 UI에서 구별. 벽 길이를 늘이려면 양옆 직각 벽을 이동한다.
- 모서리 직접 드래그는 MVP에서 지원하지 않아도 된다. 지원한다면 동일한 직각/검증 규칙을 만족해야 한다.
- **부호 규약:** `offsetMm > 0`은 외부 법선 `nOut` 방향(= 바닥 면적이 늘어나는 방향), `< 0`은 `nIn` 방향이다. 함몰 안쪽 벽을 `+`로 옮기면 홈이 얕아진다. UI는 “바깥쪽 +N mm / 안쪽 −N mm”처럼 방향을 글자로도 표시한다.
- **드래그 스냅:** 절대 좌표가 아니라 **시작 좌표 기준 오프셋**을 격자 배수로 맞춘다(격자에 맞지 않는 기존 벽이 드래그 시작 순간 튀지 않게).
- **선택 영역:** 벽의 클릭 판정 폭은 화면 기준 최소 12 CSS px로 유지한다. Konva `hitStrokeWidth`가 Stage 스케일과 함께 커지는 경우 `12/zoom` 실측 단위로 보정하거나 별도 화면 오버레이를 사용하고 여러 배율에서 실제 hit width를 검증한다.
- 벽 segment key는 **현재 polygon의 시작 vertex id** 기반으로 계산하거나 현재 인덱스를 사용하되, 도형 변경으로 삭제된 segment를 선택 상태에 남기지 않는다.

## 5. 함몰·돌출과 ㄱ·ㄷ 모양 만들기 (가장 중요한 기능)

### FR-010 — 벽 일부 함몰/돌출 생성
- 사용자는 좌측 `함몰 만들기` / `돌출 만들기` → 벽 선택 → 시작 위치/폭/깊이를 입력 또는 캔버스에서 **길이 방향/법선 방향 두 단계 드래그**.
- 선택한 변 `A→B` 길이를 `L`, 시작 위치를 `s`, 폭을 `w`, 깊이를 `d>0`라고 정의.
- 제한: `s ≥ 100`, `w ≥ 100`, `L-(s+w) ≥ 100`, `d ≥ 100` mm. 숫자 입력은 정확한 mm, 드래그는 설정된 스냅.
- 시작 점 `S=A+t*s`, 끝 점 `E=A+t*(s+w)`; `n = nIn`이면 **함몰(실내 사용 가능 바닥 면적 감소)**, `n = nOut`이면 **돌출(바닥 면적 증가)**.
- 원래 `[A,B]`를 `[A,S,S+n*d,E+n*d,E,B]` 경로로 바꾸되 A와 B의 기존 id는 유지하고 신규 S·S+n*d·E+n*d·E에는 서로 다른 신규 id를 부여한다. 꼭짓점 중복 없이 새 polygon 전체를 정규화·검증한 뒤 Undo 1건으로 커밋한다. 예외/범위/교차/100mm 미만이면 원자적 취소한다.
- 처음 생성하는 UI는 중앙 시작 기본값 `s=Math.floor((L-w)/2)`mm를 제안하고, 사용자가 시작 위치·너비·깊이를 수정할 수 있어야 한다. 홀수 차이에서 양쪽 여백은 1mm 차이 가능하며 **모든 신규 꼭짓점이 정수 mm**여야 한다.
- 생성 후 수정: 새로 만들어진 수평/수직 벽 조각을 선택해 드래그하거나 **세그먼트 법선 오프셋(mm)**을 입력해 폭/깊이를 조정한다. 홈을 되돌리는 드래그는 정규화로 합법적인 4꼭짓점 병합이 되며 원래 시작점 id를 우선 유지한다. **원래의 notch를 독립 객체로 저장하지 않으므로 “노치 폭/깊이 일괄 수정” 버튼을 실제로 구현하지 않았다면 표시하지 않는다.**
- 모든 변경에서 이전 유효 폴리곤이 source-of-truth이며 빨간 ghost는 저장하지 않는다.
- 면적 변화: 다른 벽과 겹침 없는 단순 경우 `함몰 -w*d`, `돌출 +w*d`. `mm²`에서 `㎡`로 정확히 변환.
- **함몰은 벽 표면만 안으로 파인 그림이 아니라 바닥 polygon 경계 자체의 오목한 영역**이다. 벽 두께에 의한 안쪽 돌출 또는 실내 기둥은 MVP가 아님.

### FR-011 — ㄱ자·ㄷ자 프리셋의 명확한 정의
- **ㄱ자(L형):** 방의 외곽 모서리에서 일부 사각형을 제거한 단일 연결 공간. 일반적인 ‘벽 중간 함몰’과 동일하지 않음. 별도 프리셋으로 제공.
- **ㄷ자(U형):** 한 변의 중간에서 큰 사각 홈이 들어간 형태. 단일 연결 공간이고 구멍이 아님.
- 반드시 `직사각형`, `ㄱ자`, `ㄷ자`, `돌출 방`의 실제 polygon 샘플을 제공(선택 시 기존 프로젝트 덮어쓰기 확인).
- 프리셋 좌표/면적(단위 mm):
  - 직사각형 `[(0,0),(4200,0),(4200,3400),(0,3400)]` → **14.28 ㎡**
  - ㄱ자 `[(0,0),(4200,0),(4200,3400),(1600,3400),(1600,2200),(0,2200)]` → **12.36 ㎡**
  - ㄷ자 `[(0,0),(1200,0),(1200,1000),(2400,1000),(2400,0),(4200,0),(4200,3400),(0,3400)]` → **13.08 ㎡**
  - 돌출 `[(0,0),(4200,0),(4200,3400),(1000,3400),(1000,4000),(0,4000)]` → **14.88 ㎡** (폭 1000 × 깊이 600의 하단 돌출)
- 프리셋은 모두 정규 방향으로 저장되어야 한다. 삽입 순서가 반대라면 정규화한다.
- 정규 4200×3400 방 상단에 폭 800, 깊이 500 **중앙 함몰** → 13.88㎡. **같은 폭 800×깊이 500의 돌출** → **14.68㎡**. 폭 1000×깊이 600의 별도 돌출 → **14.88㎡**. 서로 다른 입력에 대해 서로 다른 면적을 강제한다.
- ‘상단 벽 800mm 함몰’만으로 항상 ㄱ자가 되는 것처럼 설명하지 않는다. UX와 테스트에서 구별한다.

### FR-012 — 2D 치수선·그리드
- 현재 polygon의 bbox 전체 W/D, 선택된 벽 길이, 마우스 드래그 오프셋, 함몰/돌출 폭·깊이, 바닥 면적 표시.
- 좁은 변은 자동 생략할 수 있으나 선택한 벽의 길이·상세 정보는 우측 속성에서 항상 볼 수 있어야 함.
- 기본 그리드 100mm, 켜기/끄기; 스냅 10/50/100/500mm 선택, 켜기/끄기.
- **[v3] 화면 조작 기본값은 “휠 = 줌”(포인터 기준)**이며 상단바 토글로 “Figma 방식”(휠 = 이동)을 선택할 수 있다. 비전문 사용자가 휠로 줌이 안 되면 혼란스럽기 때문이다. 두 모드 모두 지원:
  - 줌: `Ctrl/Cmd+휠`, `Alt(Option)+휠`, 트랙패드 핀치. 많은 환경에서 핀치는 `ctrlKey=true`인 `wheel`로 전달되지만 브라우저·장치별로 다르다. 캔버스 wheel 리스너는 `{ passive: false }`로 등록하고, 실제 받은 이벤트에만 `preventDefault()`를 적용해 페이지 확대를 막으며 편집 영역 밖에서는 브라우저 기본 동작을 보존한다. Safari의 비표준 `gesturechange` 이벤트는 기능 탐지 후 대체 경로로 처리한다. 확대/축소 버튼은 항상 대체 조작으로 제공한다.
  - 이동: 휠/두 손가락 스크롤(Figma 방식), `Shift+휠`(가로), `Space+드래그`, 중간 버튼 드래그. **[v3]** `Space` 팬은 캔버스에 포커스가 있고 포커스된 `<button>`/입력이 없을 때만 동작하며(그 외에는 Space가 버튼 클릭이므로 가로채지 않는다), 활성 상태에서 `preventDefault()`로 페이지 스크롤을 막는다.
  - 줌 기준점은 항상 포인터 위치. 배율은 `zoom *= exp(-deltaY * k)`로 계산하고 `deltaMode`(픽셀/줄/페이지)를 정규화하며, 이벤트 1회당 변화량과 전체 배율에 상한을 둔다.
  - 단축키: `Ctrl/Cmd+=` 확대, `Ctrl/Cmd+-` 축소, `Shift+0` 100%, `Shift+1` 전체 맞춤(= `F`), `Shift+2` 선택 항목에 맞춤. 편집기 영역에 포커스가 있을 때만 브라우저 기본 확대를 가로챈다.
  - “휠 = 줌” 모드: 휠이 곧 줌, `Shift+휠` 가로 이동. “Figma 방식” 모드: 휠 = 세로 이동, 줌은 `Ctrl/Cmd+휠`·`Alt+휠`·핀치. 선택값은 UI 설정 키(`roomfit3d:v2:<import.meta.env.BASE_URL>:ui`)에 저장해 새로고침 후 유지하며 프로젝트 JSON에는 넣지 않는다.
- 화면 바깥으로 방이 사라져도 리셋 버튼으로 복원.
- 줌 최소/최대는 별도 UI 설정값(예: 0.02~1.5 px/mm)으로 고정; 실측 데이터와 무관.
- 화면 기준(휠 위치)을 중심으로 줌하는 것이 우선. 구현한 뷰 로직은 배포된 앱에서 검증.
- 클릭/드래그 분기 4px 내외. `Esc`로 임시 편집 취소.

### FR-013 — 편집 도구 상태 머신과 취소 규칙 (P0)

- 도구 `select | wallMove | indent | protrude | furniture`는 상호 배타적. 도구 변경, Esc, pointercancel, 창 비활성화, 다른 프로젝트 교체 시 현재 preview를 버리고 `idle`로 돌아가며 프로젝트·히스토리는 불변이다.
- 함몰/돌출 2단계 드래그는 `idle→wallSelected→spanPreview→depthPreview→commit/abort`. 숫자 입력 대안은 `wallSelected→formValid→commit`. 단계 중 도구 변경/화면 전환은 확인 없이 임시 preview만 취소한다. 입력 필드에는 지정 범위와 단위, 양/음 방향을 항상 표시한다.
- 벽 이동은 `idle→draggingCandidate→commit/abort`; 가구는 `draggingCatalog|draggingExisting|resizing→commit/abort`. 마우스가 Stage 밖으로 나가면 유령만 표시하고 커밋은 금지; 정상 `drop` 이외 포인터 종료는 rollback. 스냅을 끄면 벽은 mm 정수, 가구 중심은 0.5mm 배수로 커밋한다.
- 모달이 열릴 때 캔버스 단축키 정지, 포커스는 모달에 가두고 Esc로 닫는다. HTML 숫자 입력이 활성인 동안 `V/W/I/P/R/F/Delete` 등은 앱 명령을 실행하지 않는다.
- 한 화면의 데이터는 `room/furniture` 한 벌이며 2D·3D 탭은 그 데이터를 표시하는 뷰만 바꾼다. 3D 탭에서는 벽/가구 편집 버튼을 비활성화하는 대신 사용자에게 `2D에서 편집` 링크/설명을 제공한다.

## 7. 가구 DnD·선택·크기·회전

### FR-020 — 카탈로그에서 2D로 가져오기
1. 클릭 추가: 화면 중심에 가까운 **유효 위치**를 찾는다(불가하면 ‘배치 가능한 위치 없음’). 생성·선택·속성 표시까지 실제 동작.
2. HTML 카탈로그에서 드래그 → React Konva Stage 위로 포인터 이동 → 실측 W×D의 **ghost**를 표시 → 유효한 실내 지점에서만 커밋.
3. 캔버스는 HTML5 드롭과 Konva Stage의 이벤트가 다른 계층이다. **DOM `clientX/clientY`에서 컨테이너 사각형을 빼고, stage pan/scale을 역변환**해 world(mm)를 구한다. `offsetX`, 캔버스의 CSS pixel, Stage x/y를 혼용하지 않는다.
4. Stage가 줌 0.5x/2x 또는 팬된 상태에서도 **눈에 보이는 포인터 아래의 정확한 mm 중심점**으로 드롭되어야 한다.
5. 드래그 중 유효 위치: 파란/녹색 ghost; 무효 위치: 빨간 ghost + ‘벽 밖입니다’ 또는 ‘다른 가구와 겹칩니다’. 카탈로그에서 포인터가 벗어나거나 `Esc` 시 ghost 정리.
6. 배치 확정의 유효성은 미리보기의 동일한 `validatePlacement()`로 판단. 별도 임시 단순 로직 사용 금지.
7. HTML5 DnD 함정: `dragover` 중에는 `dataTransfer.getData()`를 읽을 수 없으므로 드래그 시작 시 `catalogId`를 store/ref에 보관한다. `dragover`에서 `preventDefault()`를 호출해야 `drop`이 발생한다. 좌표 변환은 `stage.setPointersPositions(e)` 방식이든 수동 역변환이든 **한 경로만** 쓰고 DECISIONS.md에 기록한다.
8. HTML5 DnD는 터치에서 동작하지 않는다. 1번의 클릭 추가를 터치·키보드 사용자의 정식 대체 경로로 유지한다. E2E는 Playwright `locator.dragTo` 또는 DragEvent 직접 dispatch로 검증하되 브라우저별 동작 차이를 확인한다.

### FR-021 — 모델 위치와 실제 footprint
- 모든 가구 인스턴스 `position`은 **바닥 footprint 중심 (x,y, 0.5mm 배수 — §3.1 [v3])**. 다른 모든 치수는 mm 정수다.
- `rotationDeg=0|180`: 세계좌표 가로 `widthMm`, 세로 `depthMm`. `90|270`: 세계좌표 가로 `depthMm`, 세로 `widthMm`.
- 축정렬 footprint: `minX=x-worldW/2`, `maxX=x+worldW/2`, `minY=y-worldD/2`, `maxY=y+worldD/2`. 홀수 치수일 때 `.5mm` 경계는 정상이며 반올림하지 않는다.
- 2D 가구 도형에 이름, 회전 방향, 실제 크기 라벨 표시. 클릭하면 우측 속성 및 조절 핸들.
- 가구 이동: 일반 drag는 그리드 스냅, 최종 유효 위치만 커밋. 스냅 OFF 시 중심을 0.5mm 배수로 커밋. `Esc` 또는 무효 드롭은 시작점 복구.
- 스냅 기준은 중심이 아니라 **footprint 좌상단 `(minX,minY)`** 이다. 스냅 후 중심 = `snappedMin + worldW/2`이며 0.5mm 배수라 홀수 W/D에서도 가장자리가 격자·벽에 **정확히** 일치한다 [v3]. 스냅 후보는 그대로 `validatePlacement`로 재검증한다. `§3.5`, AC-62, AC-85 참조.

### FR-022 — 편집/회전/리사이즈
- 우측: 이름, 위치 X/Y, W/D/H, 색상(허용된 단색), 0/90/180/270 회전, `원래 치수`, 복제, 삭제.
- 폭/깊이/높이 숫자 입력은 **스냅 없이 정확한 mm**. 파싱 중 입력 중간값은 로컬 UI 입력 상태에 보관하고, blur/Enter/확인 시 검증하고 커밋. 빈 숫자 입력을 0으로 즉시 바꾸지 않는다. 숫자 입력은 천 단위 쉼표·공백(`4,200`)을 제거한 뒤 정수 검증한다.
- 선택된 가구는 **2D 리사이즈 핸들**을 제공한다. MVP는 4개 모서리 핸들이면 충분. 반대편 코너를 고정한 채 W/D와 중심을 계산하고, 90° 회전 상태에서도 로컬 W/D가 올바르게 수정되어야 한다.
  - 구현 권장: Konva 노드는 회전시키지 않고 **세계축 정렬 footprint(worldW×worldD)** 사각형으로 그린다(방향은 별도 표식). 핸들 결과의 worldW/worldD는 `rotationDeg`가 90/270이면 각각 `depthMm`/`widthMm`으로 되돌려 저장한다. `Transformer`를 쓰면 `rotateEnabled=false`.
  - 반올림 [v3]: W/D는 정수로 반올림하고, 반대편 코너를 고정한 채 `중심 = 고정 코너 ± 반치수`로 계산하므로 중심은 자동으로 0.5mm 배수가 되고 고정 코너는 움직이지 않는다. **반올림한 뒤의 후보**를 검증·커밋한다.
- 핸들 드래그 중 치수가 100mm 미만이거나 배치 무효이면 빨간 프리뷰, 커밋 취소. Konva `Transformer` 기본 scale 값이 치수로 저장되는 실수를 방지; 모델 W/D로 반영 후 node scale은 1로 재설정.
- `R` 또는 속성 버튼으로 90° 회전. 회전 시 footprint와 검사 결과 즉시 변경; 무효하면 회전 취소. 모델 로컬 W/D는 회전 때문에 맞바꾸어 저장하지 않으며 3D yaw 부호는 §3.5를 따른다.
- 삭제/복제/이동/크기 변경은 Undo/Redo 가능. 가구 이름은 사용자가 수정 가능.

### FR-024 — 가구 배치 작업 공통 명령 (P0)

- `addFurniture`, `moveFurniture`, `resizeFurniture`, `rotateFurniture`, `duplicateFurniture`, `resetFurnitureSize`는 입력/치수/ID 검증 → 후보 world footprint 계산 → `validatePlacement` → 성공 시 단일 커밋을 공유한다. 예외는 `{ok:false, issues}`로 반환해 화면/핫키/2D DnD 모두 같은 사유를 표시한다.
- 복제는 원본 중심 주변 100mm 격자를 거리순(상하좌우·대각, 고정된 tie-break)으로 탐색하며 최대 1000개 후보를 검사하고, 못 찾으면 `복제 위치 선택` ghost 모드로 전환한다. **기존 가구와 겹친 채 자동 생성하거나 원본을 이동시키지 않는다.** 공간이 없으면 취소하고 안내한다.
- 클릭 추가는 뷰 중심 근처부터 유효 후보를 찾으며 실패할 경우 같은 ghost 배치 모드로 전환할 수 있다. 카탈로그는 초기에 20개 기본 프리셋, 3D 외형은 모든 `kind`가 최소 프리미티브로 보인다. sample sizes는 제품 구매를 보장하는 실제 제품 규격이 아니다.
- 카탈로그 DOM 드래그는 `dragstart`의 catalogId를 ref에 보관 → Stage 컨테이너 `dragover`에서 `preventDefault`, CSS 좌표 역변환/ghost 갱신 → `drop`에서 같은 검증 함수 → `dragend|Escape|pointercancel|blur|toolChange`에서 ref·ghost 해제. `dataTransfer.getData()`는 dragover에서 읽지 않는다. 2D 내부 drag는 HTML DnD와 별도 이벤트로 처리한다.
- 이름·색상 변경과 삭제는 배치가 무효인 기존 가구에도 허용한다. 새 위치/W/D/H/회전은 최종 상태가 **모두 유효해야** 커밋한다. 벽 변경이 기존 가구를 무효로 만들어도 해당 가구는 원위치에 남는다.

## 8. 충돌·경고 엔진 (정확성 최우선)

### 8.1 구조 유효성과 배치 유효성을 구별
- **구조 유효성:** polygon 점·벽·면적·치수·ID 등 프로젝트 자체의 유효성. 잘못된 polygon은 저장/가져오기/확정 금지.
- **배치 유효성:** (A) 가구 footprint가 방 바닥 내부에 전부 포함되는가, (B) 다른 가구와 **양의 면적**으로 겹치는가.
- **벽 이동·방 높이 변경으로 인한 기존 가구 무효:** room 구조가 합법이면 방 편집 자체는 허용하며 기존 가구에 경고 표시(높이 축소 시 `TOO_TALL` 포함). 가구를 자동 삭제/이동시키지 않음.
- **새 가구 추가/기존 유효 가구의 새 위치·크기·회전:** 무효가 되면 커밋 금지 및 이전 상태 복구.
- **이미 무효가 된 가구:** 끌어 유효한 위치에 드롭해 복구 가능; 무효 위치를 경유하는 드래그 프리뷰는 허용하되 커밋은 새 위치가 유효할 때만. 유효 위치가 없다면 가구 삭제 또는 방 확대 방법을 안내.
- **비기하 편집 허용:** 이름·색상 변경과 삭제는 가구가 이미 무효여도 항상 허용한다. 검증으로 막는 대상은 가구의 위치·크기(W/D/H)·회전 변경뿐이다(방 자체의 합법적 구조·높이 편집은 기존 가구 경고를 발생시켜도 허용).
- 가구끼리 **경계만 닿는 것**은 허용. 방 경계에 닿는 것은 허용. 실제 양의 면적 교차/실내 밖 점유 면적이 있으면 금지.
- **가구 높이가 방 높이를 초과**하면 배치 오류로 처리(벽 높이 수정이나 가구 높이 수정으로 해결). 바닥 높이는 0으로 고정(적층 가구 P1 이후).

### 8.2 권장 구현 알고리즘(MVP의 직각·90°에 최적화)
1. `getFurnitureRect(item)`로 회전 후 세계 축에 정렬된 footprint를 순수 함수로 얻는다.
2. 사각형과 polygon의 포함 검사는 **꼭짓점 4개만 point-in-polygon 하지 않는다**. 오목한 홈을 가로지르는 경우 놓친다.
3. 정확한 한 방법: **축정렬 격자 분할 검증**. 해당 가구 rect의 X 양끝 및 그 안에 있는 room polygon 모든 꼭짓점의 X를 정렬/중복 제거하고, Y도 똑같이 한다. 생성된 열린 셀의 중점들을 `pointInOrthogonalPolygon`으로 검사. 셀 면적이 양수이며 중점이 밖이면 가구는 실내 바닥 밖 면적을 포함한다 → 배치 거부. 직각 도형에서는 polygon 경계가 그 셀 내부를 가로지르지 않으므로 정확하다.
4. 가구 간에는 축정렬 사각형 intersection의 `overlapX = min(maxX)-max(minX)`, `overlapY=...`을 계산하여 **두 값 모두 0보다 클 때** 겹침. 정확한 mm·0.5mm 좌표 계산을 허용하며 1mm의 가짜 공차로 겹침을 허용하지 않는다.
5. `epsilon`은 부동소수 계산상의 미세 오차(예: `1e-9` mm)를 다루는 보조 값일 뿐, 실측 1mm 겹침을 허용하는 면죄부가 아니다. 계산이 정수/반정수이면 가능한 한 정확 비교.
6. 오목한 방에서 `네 모서리가 모두 실내인데 사각형 일부가 함몰 구간을 가로지르는 경우`를 반드시 unit test.
7. 유효성 검사 API 결과 예시: `{ valid:boolean, issues:[{ code:'OUTSIDE_ROOM'|'FURNITURE_OVERLAP'|'TOO_TALL'|'INVALID_DIMENSIONS', message, targetId?, details? }] }`. 시그니처 예: `validatePlacement(room, furniture, candidate, { ignoreId })` — 이동·리사이즈 중인 자기 자신과의 겹침을 `ignoreId`로 제외한다. 파생 경고용으로 전체 가구를 한 번에 검사하는 `validateAllPlacements(room, furniture)`도 순수 함수로 둔다.
8. `getRoomArea`, `validateRoomPolygon`, `moveWall`, `addNotch`, `getFurnitureRect`, `containsRectInRoom`, `intersectRects`, `validatePlacement`, `getNearestClearance`는 DOM/React/Three와 분리한 **순수 함수**여야 한다.

### 8.3 경고와 최소 간격
- 선택 가구 주변에서 방 경계/다른 가구까지의 **최소 이격거리(mm)**를 계산해 표시. 간격 0mm는 경계 접촉, 겹침이면 별도 ‘겹침’ 오류.
- “벽을 몇 mm 넘음”과 같은 구체적인 정량 메시지는 실제 계산 근거가 있을 때만 표시. 정량화가 어렵다면 ‘방 경계 밖으로 나갑니다’라고 정확히 안내.
- MVP는 **하드 오류(배치 불가)**와 **구조 변경 후 남아 있는 기존 배치 오류**를 구별. 법규 수준의 통행 폭 권고·문 여닫이 간격은 MVP에 섞지 않는다.
- 방을 수정할 때 기존 가구들의 오류는 파생 계산으로 실시간 업데이트. 데이터 모델에 저장된 오래된 경고를 진실로 쓰지 않는다.

### 8.4 [v3] 확정 정의: 간격 측정 `getNearestClearance` (FR-025)
- 선택 가구 footprint `R=(minX,minY,maxX,maxY)`의 **네 방향 자유 거리**를 반환한다: `{left,right,up,down}` (mm, 접촉이면 0; 방 경계가 항상 존재하므로 유한).
- 방향 `+x`(right): 스트립 `(maxX,∞)×(minY,maxY)`(열린 구간) 안에서 만나는 가장 가까운 장애물까지 `x−maxX`의 최솟값. 장애물 = ① 다른 가구 rect 중 y구간이 `(minY,maxY)`와 **양의 길이**로 겹치고 `minX_b ≥ maxX`인 것 → `minX_b−maxX`, ② polygon의 **수직 변** 중 `x ≥ maxX`이고 y구간이 `(minY,maxY)`와 양의 길이로 겹치는 것 → `x−maxX`. 나머지 세 방향은 대칭이다(직각 polygon에서는 안쪽 이동이 반드시 수직/수평 변을 지나므로 이것으로 충분). 최솟값을 만든 대상 id도 함께 돌려줄 수 있다.
- UI 표기는 **`도면상 최단거리`**로 하여 법규 통로 폭·실제 설치 여유와 혼동하지 않게 한다. 이미 무효인(밖에 나갔거나 겹친) 가구에는 거리 대신 “먼저 배치 오류를 해결하세요”와 해당 오류를 보인다.
- 예: 4200×3400 방에 1500×2000 침대 중심 `(1050,1250)` → `left=300, up=250, right=2400, down=1150`(UT-GEO-12, AC-74).

### 8.5 [v3] 확정 정의: ID 생성과 결정론
- 모든 id 생성은 주입 가능한 `IdGenerator`(`() => string`) 한 곳으로 한다. 프로덕션은 `crypto.randomUUID()`(없으면 `Date.now`+난수 폴백), **테스트는 `seq-1, seq-2…` 결정론 생성기**를 주입한다. 순수 함수(`addNotch` 등)는 생성기를 인자로 받는다(AC-90).
- JSON 불러오기 시 polygon 방향이 반시계(shoelace<0)이면 거부하지 않고 **뒤집어 정규 방향으로 정규화**한 뒤 검증한다(vertex id 보존, §3.3 4항의 변경 내역 표시). 수평/수직이 아니거나 구조가 틀리면 거부.

### FR-025 — 정확한 포함·겹침·이격 계산 (P0)

1. `getFurnitureRect`: 회전이 0/180이면 worldW=width, worldD=depth, 90/270이면 교환. 중심은 0.5mm 배수, 끝 좌표는 정수 또는 `.5`다. `xMin<xMax`, `yMin<yMax` 필수.
2. **오목한 방 포함:** rect의 [xmin,xmax]와 polygon 꼭짓점 중 이 범위에 있는 모든 x를 정렬한 `xs`, y도 `ys`로 만든다. 모든 열린 셀 `(xs[i],xs[i+1]) × (ys[j],ys[j+1])`의 중점이 실내(경계점 아님)면 포함; 외부 중점이 하나라도 있으면 실패. 실내 경계에 대한 점·선 접촉은 허용. 정수/반정수에서 `eps=0` 비교를 기본으로 한다. 각 선분이 축정렬이므로 열린 셀 내부를 경계가 관통할 수 없다는 것이 정확성 근거다.
3. **겹침:** 두 가구 rect가 `overlapX>0 && overlapY>0`일 때만 `FURNITURE_OVERLAP`. `overlapX=0` 등 정확한 접촉은 정상. 높이 조건은 `heightMm <= wallHeightMm`.
4. **반례:** ㄷ자 `[(0,0),(1200,0),(1200,1000),(2400,1000),(2400,0),(4200,0),(4200,3400),(0,3400)]`에 rect `(xmin=1000,ymin=700,xmax=2600,ymax=1300)`를 두면 네 꼭짓점 모두 실내지만 x=1200~2400·y=700~1000은 실외이므로 **거부**한다.
5. `getNearestClearance`는 §8.4의 네 방향 자유 거리 정의를 따른다. 벽·다른 가구에 대한 거리는 모두 같은 함수에서 나오며, 다른 정의(유클리드 최단거리 등)를 UI나 테스트에 병행하지 않는다.
6. 구조 변경 후 `validateAllPlacements`가 전 가구를 다시 검사한다. `validatePlacement`는 단일 순수 함수이며 새 후보와 기존 invalid 가구 간의 겹침도 거부한다. 겹침이 없는 정상 위치로 이동해 복구 가능한 경로는 유지한다.
7. UI는 벽 외부/가구 겹침/높이 초과를 한국어로 구별한다. 경고는 저장하지 않는 파생 값이며 커밋 전/후 동일 함수로 계산한다.

## 9. 3D 구현 명세

### FR-030 — 바닥/벽의 실제 기하학
- Render: Three.js + React Three Fiber + Drei. 2D polygon을 `mm/1000`으로 변환하여 **오목한 바닥 면도 정확히 삼각분할**. 단순 사각형 바닥으로 대체 금지.
- **[v3] 바닥 생성 확정 레시피:** `new THREE.Shape(polygon.map(p => new THREE.Vector2(p.x/1000, -p.y/1000)))` → `new THREE.ShapeGeometry(shape)`(내부 earcut, 항상 +Z 향함) → `geometry.rotateX(-Math.PI/2)`. 회전 행렬 `y'=y·cosθ−z·sinθ, z'=y·sinθ+z·cosθ`(θ=−π/2)에 의해 점 `(x,−y,0)→(x,0,y)`(즉 z3d=y2d/1000, §3.1과 일치)이고 노멀 `(0,0,1)→(0,1,0)`(위). `rotateX(+π/2)`나 y 부호를 안 뒤집는 방식은 z가 반전되거나 노멀이 아래를 향하므로 금지. 2D 정규 polygon(화면 시계 방향, shoelace 양수)을 `(x,0,z)`에 그대로 올려 삼각분할하면 노멀이 아래로 향할 수 있으므로, 어떤 경로든 생성 삼각형의 Y 법선을 테스트로 검사하고 아래를 향하면 인덱스를 뒤집는다. 테스트: 모든 삼각형의 노멀 y>0, 정점 z가 2D y/1000과 일치, 삼각형 면적 합 = polygon 면적(Float32 버퍼 기준 허용 오차 `1e-6 ㎡`, §17.4 UT-3D-01~03). 바닥 `material.side=FrontSide`, 방 외곽 바깥에는 지면을 그리지 않는다(함몰 구간은 빈 공간).
- 각각의 벽 선분에 `wallHeightMm`과 `wallThicknessMm`이 적용된 직육면체를 만든다. **polygon 경계는 벽의 실내 면**으로 정의하고 두께는 항상 외부 법선 `nOut`으로 적용해 유효 실내 면적을 줄이지 않는다.
- 모서리 정책(용어: 실내각 90° = 볼록 모서리, 270° = 오목 모서리). 각각의 벽은 경계의 **실내면**에서 외부 법선으로 두께 `t`만큼 생성한다. 변마다 바깥쪽으로 두께를 준 직육면체만 쓰면 **볼록 모서리에는 `t×t` 정사각 틈**이 생기고, **오목 모서리와 폭 `2t` 미만의 홈에서는 박스끼리 겹쳐** z-fighting이 난다. 따라서 §9.1 FR-033의 **2D 벽띠 합집합 격자 분할**로 볼록 코너 패치를 포함한 중복 없는 최종 상단/측면 삼각형 메시를 만든다. 어떤 패치도 실내 쪽(`nIn`)으로 침범하면 안 되며, 외벽 메시가 실내 polygon의 양의 면적에 침범하면 빌드 실패다. 외곽 오프셋 링을 `ExtrudeGeometry`로 만드는 대안은 폭 `2t` 미만 홈에서 링이 자기교차하므로 쓰지 않는다. 플로어 경계는 바뀌지 않는다.
- 벽마다 `heightMm`은 동일(P0). 가구는 정확히 바닥 y=0 위에 놓인다. 3D 가구 외곽 bbox가 해당 인스턴스의 W/D/H를 넘지 않도록 자체 프리미티브 구성.
- 컬러는 가구를 알아볼 수 있을 정도로만 차별화(침대·소파·책상·식탁·냉장고·옷장·세탁기 등 최소 대표 유형별 외형). 모든 20개 가구가 표시되어야 한다.
- 3D 렌더러는 `ProjectData.room`·`ProjectData.furniture`를 읽는 **파생 뷰**이며, 독자적으로 영속 공간 데이터를 수정하거나 저장하지 않는다.
- 2D에서 치수, polygon, 가구가 바뀔 때 3D에 최신 상태가 나타나야 한다. 프레임 성능 때문에 프리뷰 시 debounce/RAF는 허용하되 최종 커밋 후 동기화가 빠지면 안 된다.

### FR-031 — 카메라 및 선택
- **[v3] 초기 카메라 확정값:** bbox 중심 `c=((minX+maxX)/2000, (minY+maxY)/2000)`(m), 대각 `D=hypot(bboxW,bboxD)/1000`(m). `target=(c.x, wallHeightMm/2000, c.z)`, 시선 방향 `dir=normalize(0.6, 0.7, 0.8)`, `position = target + dist·dir`. 거리는 `dist = max(1.2·D, 현재 3D 캔버스 종횡비에서 방 bbox(바닥 4점 + 벽 높이)의 8꼭짓점이 모두 NDC ±0.95 안에 들어오는 최소 거리)`로 구한다(fov 45° 수직 기준으로 투영해 이분 탐색하거나 닫힌 식으로 계산). fov 45, near 0.1, far 200, `maxPolarAngle=π/2−0.05`, `minDistance=0.5`, `maxDistance=6·D`. 조명: `ambientLight 0.6` + `directionalLight 0.8`(위치 target+(5,10,5)), 그림자는 기본 끔(성능). `전체 보기`/`카메라 초기화` = 위 값 재계산. 참고값: 기본 방 4200×3400×2400에서 `D=5.4037`, `1.2·D=6.4844m`는 세로 방향이 넘치므로(|ndc|≈1.19, 16:10과 1:1 동일) 적용 거리는 종횡비 1 이상에서 `7.775m`, 종횡비 0.8에서 `9.347m`, 0.6에서 `12.206m`다. 테스트는 같은 식으로 계산한 값과 `1e-6` 이내로 일치하고 8꼭짓점이 NDC 안인지 확인한다(AC-28).
- 최초 3D 진입: 방 전체가 보이는 3/4 카메라, 타깃은 bbox 중심(높이 적절하게 적용).
- `OrbitControls`: 왼쪽 드래그 회전, 휠 줌, 우클릭 팬(플랫폼 제약 고려), 각도 제한으로 바닥 아래로 뒤집히지 않게 함.
- `전체 보기`, `카메라 초기화` 버튼이 정상 동작.
- 3D 클릭 선택·하이라이트는 **선택 사항**이다(구현하면 읽기 전용 선택까지만, 선택 상태는 2D와 공유). **3D에서 직접 가구 드래그**는 MVP 의무 아님. P0의 직접 조작은 2D에서 완성.
- 3D 화면과 상단 2D 모드를 오갈 때 프로젝트 변경이 없어야 한다.

### FR-032 — 로딩·폴백·성능
- `viewer3d`는 가능하면 `React.lazy`로 지연 로딩해 초기 2D 화면의 과도한 JS 다운로드를 피한다.
- WebGL 비활성, 컨텍스트 생성 실패, Three 컴포넌트 런타임 오류에 대비한 3D 경계 컴포넌트/대체 설명을 제공. 2D는 계속 정상 실행. **[v3]** Canvas 마운트 전 `document.createElement('canvas').getContext('webgl2') ?? getContext('webgl')`로 사전 검사하고, 런타임 `webglcontextlost` 이벤트(`preventDefault` 후 안내+“다시 시도” 버튼)를 처리한다. 테스트는 `getContext`를 null 반환으로 모킹한다(AC-30).

- 성능 기준은 **목표치**다. 브라우저와 사양에 따라 프레임 성능이 다르므로 수치(30fps 이상)는 실제 측정 없이 ‘달성’이라 쓰지 않는다.

### 9.1 FR-033 — 벽 모서리·오목 홈에 강한 메시 생성 (P0)

- 입력: 검증된 직각 실내 polygon, 벽 두께 `t`, 높이 `h`. 각 directed edge `A→B`에 대해 선분 양 끝을 포함한 외부 법선 방향 `t`의 **축정렬 벽띠 사각형**을 만든다. 이 사각형들만으로는 볼록 코너 외측 `t×t` 사각형이 빈다. **볼록 코너마다** 외부 사분면의 `t×t` 코너 패치를 더한다.
- 이 사각형들의 합집합을 **중복 없는 면**으로 만든다: 모든 사각형 x/y 경계의 좌표를 정렬한 grid를 만들고, 열린 셀 중심이 어느 벽띠·코너패치 안에 있는지 표시한다. 셀이 실내 바닥 polygon에 양의 면적으로 겹치면 버그로 실패. 덮인 셀의 위/아래 면을 삼각형 두 개로 구성하되, 수평 맞닿은 셀은 필요한 경우 병합한다. 측면은 이웃 셀이 비어 있는 격자 경계에만 생성한다. **중복되는 내부 면과 coplanar 중복 삼각형은 생성하지 않는다.** 꼭짓점 64개에서도 안전성 우선이며, 30벽·50가구 성능 목표를 측정한다.
- 외측 고립 조각/잘못 닫힌 링이 있는지 점검한다. 오목 270° 코너, 100~200mm 폭의 좁은 홈, `t=500mm` 경계 테스트를 포함한다. 최종 외벽의 안쪽 경계는 모델 room polygon과 일치해야 한다. 벽의 실내 면은 반드시 수직이고 h는 모든 꼭짓점에서 동일하다.
- 바닥: FR-030의 확정 레시피(`Shape(x/1000, −y/1000)` → `ShapeGeometry` → `rotateX(−π/2)`)로 만들고 생성 삼각형의 Y 법선이 모두 위(+Y)인지 검사한다(아래를 향하면 인덱스를 뒤집는다). 테스트에서 삼각형 면적 합=polygon shoelace 면적(Float32 버퍼 기준 허용 오차 `1e-6 ㎡`)과 바닥 전체가 위로 향함을 확인한다. 바닥 렌더는 z-fighting 방지를 위해 y=0에 단일 면, 벽 밑면의 중복 면은 숨겨도 된다.
- 가구: 20개 프리셋은 모두 최소 하나의 실제 Three.js geometry로 나타나고 바닥에 접한다. 높이·폭·깊이 바운딩박스는 인스턴스 실측치를 넘지 않는다. 카탈로그 `kind`에 맞는 여러 부품이 가능하지만 전체 bbox는 동일하다. `dispose()`와 React cleanup을 적용하며 WebGL 예외 시 **2D 편집은 계속 가능**하다.
- 렌더 프레임마다 새 지오메트리를 생성하지 말고 커밋된 polygon/height/thickness가 변할 때만 갱신한다. 임시 preview는 2D에서 처리하거나 적당히 throttling하고, 최종 커밋은 3D 지연 없이 업데이트한다.

### 9.2 FR-034 — 카메라·회전·2D/3D 단일 원본 (P0)

- `ProjectDataV2.room.polygon`과 `furniture`만 2D·3D 원천으로 사용한다. 3D mesh position, Konva x/y는 파생물이다. 선택 상태는 공유해도 영속 데이터는 3D에서 수정하지 않는다.
- 3D 카메라의 타깃·시선 방향·거리·fov·near/far·각도 제한·조명은 FR-031 확정값을 단일 출처로 쓴다. 화면 종횡비 변경/프리셋 변경 시 `전체 보기`는 같은 식으로 다시 계산한다. E2E는 projected corners가 NDC 내부에 있는지 확인한다.
- 2D의 +90°(화면 시계방향) = 3D의 −90° yaw. `rotationDeg=0`/`90`/`180`/`270`의 3D 가구 외형·방향 표시가 2D footprint/회전과 일치하는지 확인한다.
- OrbitControls는 read-only 카메라용; 이벤트가 사용자의 가구 편집을 시작하지 않는다. context lost/복구·WebGL 미지원/오류 경계의 테스트를 따로 둔다.

## 10. 데이터 모델 및 상태 계약

### 10.1 TypeScript 영속 스키마(개념 코드, 실제 구현은 Zod와 일치시킬 것)
```ts
type Millimeters = number; // 범위 검사된 integer (가구 position.x/y만 0.5mm 배수 허용, §3.1)
type RotationDeg = 0 | 90 | 180 | 270;
type PointMm = { id: string; x: Millimeters; y: Millimeters };

type FurnitureKind =
  | 'bed' | 'sofa' | 'table' | 'desk' | 'wardrobe'
  | 'storage' | 'refrigerator' | 'washingMachine' | 'chair' | 'other';

type Room = {
  id: string;
  name: string;
  polygon: PointMm[]; // 첫 점 중복 없는, 직각 단순 다각형
  wallHeightMm: Millimeters;
  wallThicknessMm: Millimeters;
};

type FurnitureItem = {
  id: string;
  catalogId: string;
  kind: FurnitureKind;
  name: string;
  position: { x: Millimeters; y: Millimeters }; // 바닥 footprint 중심, 0.5mm 배수
  widthMm: Millimeters;
  depthMm: Millimeters;
  heightMm: Millimeters;
  rotationDeg: RotationDeg;
  color?: string;
};

type ProjectDataV2 = {
  schemaVersion: 2;
  id: string;
  title: string;
  createdAt: string; // ISO 8601
  updatedAt: string; // ISO 8601
  unit: 'mm';
  room: Room;
  furniture: FurnitureItem[];
  settings: {
    gridSizeMm: 10 | 50 | 100 | 500;
    snapEnabled: boolean;
    gridVisible: boolean;
  };
};
```

### 10.2 단일 진실과 UI 상태
- `room.polygon`, `furniture` 등 `ProjectDataV2`가 단일 진실. `polygon` 점에는 안정적 `id`가 있고, 선분 선택은 **각 시작점 id로 식별**하거나 각 커밋 직후 안전하게 재계산한다.
- **앱 UI 상태**: 활성 도구, 선택 항목, 2D 줌/팬, 3D 카메라, 드래그 중 ghost, 모달, 호버, 임시 수치 입력. 기본 저장 JSON에 포함할 필요 없음.
- **파생 데이터**: 방 면적, 벽 목록, bbox, 검증 이슈, 2D 화면 path, 3D mesh. 프로젝트 JSON의 신뢰할 영속 필드가 아님.
- 외부 입력(JSON)·UI 숫자 입력·상태 명령·저장 모두 스키마/도메인 검증을 공유한다. 서로 다른 제한값 정의 금지.
- ID는 §8.5의 주입 가능한 `IdGenerator` 한 곳에서만 만든다. 프로덕션은 `crypto.randomUUID()`가 사용 가능하면 사용하고 비지원 환경의 안정 대체 수단을 두며, 테스트는 결정론 생성기를 주입한다. 외부 비밀키 불필요.

### 10.3 마이그레이션 및 파일 안전
- **문서 버전 v3과 JSON 스키마 버전은 별개다.** 기존 v2 프로젝트와의 호환을 위해 `schemaVersion: 2`를 유지한다. 새 스키마를 **version 2**로 시작한다. 이미 v1 프로젝트 데이터가 있다면 migration: `{x,y}` 꼭짓점에 ID 부여, 필드 기본값 보완, v2 검증. 없으면 v1을 지원하지 않는다고 설명해도 되지만 **기존 PRD v1 JSON을 배포한 적이 있다면 복구 가능성부터 검토**.
- 어떤 버전이든 **형식 오류·잘못된 polygon·불가능한 치수·중복 ID·100개 초과·2MiB 초과**는 명확한 사유와 함께 거부.
- 하지만 **방 수정 후 기존 가구가 경계를 벗어난 상태**는 유효한 프로젝트 상태이므로, 불러오기 때 *구조적으로 합법적이지만 배치가 무효인 가구*를 무단 삭제/거부하지 않는다. 경고를 파생 표시한다.
- `JSON.parse` 결과는 **Zod `.strict()` 스키마로 알 수 없는 키를 거부**한다. `Object.assign`으로 입력 객체를 상태에 혼합하지 않는다. 객체 prototype 오염·XSS에 주의. 이름/프로젝트 타이틀은 React 텍스트 노드로만 출력하고 파일명에 안전한 문자만 사용.
- URL query / localStorage / JSON의 악의적인 데이터를 `eval`, `new Function`, `innerHTML`에 넣지 않는다.

### 10.4 프로젝트 생성 예제
- `내 첫 원룸`: 4200×3400mm, 높이 2400, 퀸 침대(중심 1050,1250) + 책상(중심 2950,2800), 서로 및 벽과 겹치지 않아야 한다.
- 위 5절의 ㄱ/ㄷ/돌출/직사각형 예제도 제공. 프로젝트명과 vertex ID는 유일하게 생성.
- 예제의 모든 가구는 검증 함수를 통과해야 하며, 성공 사례를 가짜 경고 없이 보여준다.

## 11. 상태 명령, Undo/Redo 및 편집 트랜잭션

**명령 인터페이스 예시:**
```ts
createProject(dimensions)
setRectangleDimensions({ widthMm, depthMm })
moveWallSegment({ startVertexId, offsetMm })
addNotch({ startVertexId, startOffsetMm, widthMm, depthMm, type: 'indent'|'protrude' })
addFurniture({ catalogId, position })
moveFurniture({ itemId, position })
resizeFurniture({ itemId, widthMm, depthMm, heightMm })
rotateFurniture({ itemId, rotationDeg })
duplicateFurniture({ itemId })
deleteFurniture({ itemId })
updateRoomHeight({ wallHeightMm })
updateWallThickness({ wallThicknessMm })
applyRoomPreset({ presetId })        // 확인 후 새 작업 맥락
renameProject({ title })
renameFurniture({ itemId, name })
setFurnitureColor({ itemId, color })
resetFurnitureSize({ itemId })       // "원래 크기로"
loadProject(project)                 // 새 프로젝트·예제·JSON 불러오기: 히스토리 초기화
undo()
redo()
```
- 실행 순서: `현재 프로젝트` → `변경 후보 생성(순수 함수)` → `도메인 유효성 검사` → `원자적 커밋` → `파생 상태 재계산` → `히스토리 1건 추가` → `자동 저장 예약`.
- **프리뷰는 커밋 아님**. 드래그 중 수백 번 바뀌어도 Undo 1건. Esc, 포인터 취소, 무효 드롭이면 히스토리/자동 저장 변경 없음.
- Undo/Redo는 커밋된 프로젝트 스냅샷 또는 되돌릴 수 있는 명령 기반. 최소 50단계, 새 작업 시 Redo 스택 폐기, 너무 큰 중첩 참조/직접 변형 금지.
- Undo로 복원한 프로젝트도 자동 저장(단위: 확정 상태). 2D·3D에서 같은 이전 배치가 보임.
- 현재 파일 불러오기, 새 프로젝트, 예제 교체는 과거 프로젝트로 돌아가는 Undo가 아니라 **새 작업 맥락**으로 취급하고 이전 히스토리를 초기화해도 됨. 반드시 교체 전 확인.
- UI 뷰 줌/팬은 Undo 대상에서 제외. 프로젝트 제목·가구 색상 등 편집 가능한 데이터는 Undo 대상. `settings`(그리드·스냅)는 저장은 하되 Undo 대상이 아니다. Undo 스냅샷은 `room/furniture/title` 및 되돌릴 도메인 필드만 보유하여 UI settings를 실수로 되감지 않는다. `createdAt`은 유지, `updatedAt`은 Undo/Redo 후 새 커밋 시각으로 갱신한다.
- 텍스트·숫자 입력은 키 입력마다 히스토리에 넣지 않고 blur/Enter 커밋 때 1건만 기록한다.
- Undo/Redo 뒤 존재하지 않게 된 id를 가리키는 선택 상태는 해제한다.
- 히스토리 스냅샷은 불변 업데이트의 구조 공유로 보관한다(매 커밋 deep clone 금지).

## 12. 저장과 JSON 입출력

### FR-040 — 로컬 자동 저장
- **S0(기반 단계)부터 최소 자동 저장/복구 토대 구현**. S4에서 실패 처리·내보내기·마이그레이션 고도화.
- `localStorage` 키는 `roomfit3d:v2:<import.meta.env.BASE_URL>:autosave`와 같이 네임스페이스를 적용. Pages의 다른 경로 프로젝트와 충돌하지 않게 함.
- 드래그 프리뷰는 저장하지 않는다. 사용자가 확정한 변경 후 500~1000ms debounce로 저장. `pagehide` 등에서 마지막 저장 시도할 수 있으나 브라우저 종료 시 완전한 저장을 보장한다고 주장하지 않는다.
- 저장 상태 `저장 중 / 저장됨 / 저장 실패`를 UI에서 확인할 수 있고, 실패/브라우저 제한/용량 초과 시 JSON 수동 백업을 제안.
- 복구 데이터가 손상됐거나 검증에 실패하면 **원본 키를 덮어쓰지 않고**, 가능하면 별도 키(`...:autosave-corrupt:<timestamp>`)에 사본을 저장한다. 백업도 실패하면 원본만 유지하고 JSON 복구 안내를 표시한다. 사용자가 명시적으로 처리하기 전에는 새 프로젝트로 손상된 원본 키를 덮지 않는다.
- 같은 키를 여러 탭이 쓰면 마지막 쓰기가 이긴다. `storage` 이벤트로 원격 변경을 감지한 즉시 예정된 debounce 쓰기를 **취소하고 저장을 일시중지**한 뒤 “다른 탭에서 수정됨 — 이 탭 내용 내보내기 / 다른 탭 불러오기 / 이 탭으로 덮어쓰기”를 안내한다. 덮어쓰기는 명시적 확인 후에만 허용한다. 동시에 저장된 두 탭의 완전한 무충돌 보장은 `localStorage`만으로 불가능하므로 **동시 편집은 지원하지 않음**을 명시한다.
- 새로고침 시 지원 가능한 데이터라면 그대로 복구. 브라우저 저장 데이터 삭제/다른 기기/시크릿 모드/다른 브라우저와 동기화되지 않는다는 점을 명시.

### FR-041 — JSON 파일
- 내보내기는 유효 프로젝트 **화이트리스트 필드만** 직렬화하며 확정 상태에 포함된 방·기존 invalid 가구까지 그대로 보존. 파일명은 `roomfit-<safe-title>-YYYYMMDD.json`. `safe-title`은 한글을 포함한 유니코드 문자·숫자·`-`·`_`만 남기고 경로 구분자·제어문자·`<>:"/\|?*`를 제거하며, 공백은 `-`로 바꾸고 50자로 자른다. 결과가 비면 `project`를 쓴다(한글 제목이 빈 파일명이 되지 않게).
- 불러오기: 실제 바이트 크기 검사(≤2MiB) → `JSON.parse` → 엄격한 스키마 버전 검사/지원되는 이행 → 구조 유효성·중복 id 검사 → 변경점/무효 가구 경고 요약 → 사용자에게 교체 확인 → **단일** state 교체 및 autosave. 실패 또는 사용자 취소 시 현재 project/history/selection/storage/dirty flag 모두 불변. 파일명·MIME는 신뢰하지 않고 실제 내용을 검사한다.
- 실패 시 현재 프로젝트·히스토리·로컬 자동 저장 데이터가 **절대 손상되면 안 된다**. 명확한 오류 및 재시도.
- 파일 roundtrip 테스트: polygon 점/id, 가구 id/좌표/W/D/H/회전, 프로젝트명, settings 등 **핵심 영속 필드 동일**(updatedAt 같이 변경 가능한 메타데이터는 정해진 규칙대로).
- P0는 이미지 저장/공유 링크/클라우드 동기화를 요구하지 않는다.

## 14. GitHub Pages 배포 계약

### 14.1 실제 배포 환경
- 기본 가정: 개인 계정의 **프로젝트 저장소** 이름 `roomfit-3d`, 사이트 `https://<USERNAME>.github.io/roomfit-3d/`.
- **프로젝트 페이지는 Vite `base='/<REPO>/'`**, 사용자 루트 `username.github.io` 저장소나 도메인 루트는 `base='/'`.
- 저장소 이름을 모르더라도 코드가 중단되지 않도록 `GITHUB_REPOSITORY` 환경 변수의 repo명 또는 사용자가 설정하는 `VITE_BASE_PATH`로 빌드 base 결정. 로컬 개발에는 `/` 사용 가능. `GITHUB_REPOSITORY`는 `owner/repo` 형식이므로 `/` 뒤 repo명만 쓰고, repo명이 `<owner>.github.io`로 끝나면 `base='/'`로 한다. `VITE_BASE_PATH`가 있으면 우선하며 앞뒤 슬래시를 `/repo/` 형태로 정규화한다.
- 라우팅은 단일 SPA 경로(`/`) 기반으로 하며, 프로젝트 사이트 주소 아래 다른 history URL을 요구하지 않는다. 여러 URL이 필요하면 HashRouter 방식 사용.
- JS/CSS/favicon/동적 청크/JSON 파일은 Vite base를 준수. `import.meta.env.BASE_URL` 활용; 상대/번들 import 우선.

### 14.2 워크플로와 수동 설정
- `.github/workflows/deploy.yml`: `main` push와 `workflow_dispatch`, `permissions: contents: read, pages: write, id-token: write`, Pages environment, 동시 배포 제한.
- 스텝: checkout → 지원 Node LTS setup/npm cache → `npm ci` → `npm run typecheck` → `npm run lint` → `npm run test` → `VITE_BASE_PATH=/<실제REPO>/ npm run build` **한 번** → 그 동일한 `dist`의 `index.html` JS/CSS 및 동적 청크·favicon 경로가 배포 하위 경로를 준수하는지 검사(AC-39) → configure-pages → upload-pages-artifact(`dist`) → deploy-pages. 검증 후 다른 base로 다시 빌드해서 검증하지 않은 dist를 업로드하지 않는다.
- **[v3] 2026-11-02 GitHub 공식 문서 확인 예시 버전:** `actions/configure-pages@v5`, `actions/upload-pages-artifact@v4`, `actions/deploy-pages@v4`, 아티팩트는 심볼릭/하드 링크 없는 단일 tar(<10GB). 구현 시 공식 문서(using-custom-workflows-with-github-pages)에서 다시 확인하고 더 새로운 권장 버전이 있으면 그것을 쓴다. Vite·Node 요구 버전과 react-konva peer 범위는 설치 시 `npm view <pkg> peerDependencies engines`로 확인한다. `vitest` 설정에 `exclude: ['tests/e2e/**']`를 넣어 Playwright 파일이 단위 테스트로 실행되지 않게 한다.
- GitHub 공식 Pages 액션의 **현재 안정 버전/권장 버전**을 사용. 버전 번호를 추측해 코드를 실패하게 만들지 말고 공식 문서와 빌드 로그 기준 결정.
- 사용자가 리포지토리를 만들거나 Pages를 활성화해야 하는 경우, README에 `Settings → Pages → Build and deployment → Source: GitHub Actions` 단계와 실제 repo에 맞는 URL을 명시.
- **GitHub Free 개인 계정의 비공개 저장소는 Pages 지원이 제한된다.** 기본 접근은 공개 repo이며, private repo Pages 사용 가능 여부는 GitHub 요금제와 설정을 확인한다.
- **비공개 저장소에서 배포하더라도 배포된 Pages 웹사이트는 공개될 수 있다.** 사용자 프로젝트나 실주소 같은 민감정보를 repo/정적 빌드에 넣지 않는다.
- GitHub Pages는 정적 호스팅이고 본격적인 상용 SaaS 운영 용도는 별도 검토가 필요하다.

### 14.3 '배포됨'이라고 말할 수 있는 기준
- `npm ci`, typecheck, lint, unit tests, build가 통과해야 **로컬 빌드 완료**.
- GitHub 계정 권한/원격 저장소/토큰이 없으면 **Actions 파일 작성과 로컬 빌드까지 완료했다고만 보고**한다. 원격 push/Pages 활성화·실제 URL 검증을 했다고 꾸며 쓰지 않는다.
- 원격 권한이 주어지고 push가 실제 성공하고 Actions가 초록색이며 실제 `/<REPO>/` 접속, 새로고침, 동적 리소스 로딩, 2D/3D 동작을 확인했을 때만 **배포 확인 완료**.
- 실패 시 실제 작업 로그를 근거로 무슨 단계가 실패했고 사용자가 무엇을 해야 하는지 제시.

## 15. 접근성·성능·품질·안전

### 15.1 접근성과 키보드 대체
- 주요 동작(새 프로젝트, 가구 추가, 이름/치수 수정, 삭제, 저장, 모드 전환)은 캔버스 포인터 없이 HTML 버튼/폼으로 접근 가능.
- 캔버스 드래그의 완전한 스크린리더 조작까지 MVP 의무는 아니지만, 숫자/버튼 기반의 필수 대체 경로를 보장.
- 포커스 테두리, form label, aria-live 오류/저장 상태, 모달 focus trap/ESC 닫기·확인 동작.
- 색맹/대비 배려: 유효/무효는 색 외에 아이콘과 텍스트.

### 15.2 성능
- 목표: 일반 데스크톱에서 **가구 50개·벽 세그먼트 30개**를 놓아도 반응성 양호, 3D 평균 30fps 이상을 지향. 기기의 WebGL 지원과 그래픽 사양에 따라 달라지므로 미측정 수치는 보장 금지.
- Stage/Canvas 뷰 resize 시 폭/높이 안정, 2D 드래그 핸들 위치가 안 어긋남.
- 기하 geometry 계산은 pure & memoized; 드래그 중 UI 반응을 우선하고 매 픽셀 autosave/rebuild/history 금지.
- 최종 커밋에서 모든 파생 뷰가 일관된 모델을 렌더한다.

### 15.3 보안·개인정보
- 사용자 인증/이메일/주소/결제/유료 API 없음. 서비스에 필요한 고객정보 수집하지 않음.
- 브라우저 `localStorage`를 쓰므로 **개인 PC 및 공용 PC 보안**, 데이터 삭제 가능성을 사용자에게 알림.
- 모든 JSON 입력에 크기/구조/중복 ID/범위 제한·화이트리스트 검증. XSS·프로토타입 오염 관련 입력을 실행하지 않음.
- 써드파티 이미지/폰트/아이콘 사용 시 라이선스 확인 후 README에 기록. 저폴리곤 primitive는 직접 생성.

## 16.1 S6 — 실시간 동시 편집 (MVP 이후 선택 단계)

**착수 조건:** S0~S5 게이트가 모두 통과한 뒤. 협업 코드가 없어도 MVP 전 기능이 그대로 동작해야 한다(협업 서비스 미설정·장애 시 협업 UI만 비활성).

### 목표
계정 없이 **공유 링크**로 2~8명이 같은 방을 동시에 편집한다. 타인의 커서·선택·드래그 중인 ghost가 보이고, Undo/Redo는 각자 본인 작업만 되돌린다.

### 아키텍처 결정 (DECISIONS.md에 기록)
- 정적 호스팅(GitHub Pages)을 유지한다. 서버를 직접 운영하지 않고 **외부 무료 실시간 서비스**를 쓴다. 후보: Yjs + (PartyKit, Liveblocks, Supabase Realtime 등 무료 티어), 또는 `y-webrtc`(P2P; 신호 서버 필요, 방화벽·NAT에서 연결 실패 가능하므로 실패 시 안내). 선택 근거와 무료 한도를 DECISIONS.md에 적는다.
- 서비스 공개 식별자는 빌드 환경 변수로 주입한다. 비밀키는 저장소·번들에 넣지 않는다.
- 새 의존성(`yjs` 등)은 §13 허용 목록 밖이므로 이 단계에서만 추가하고 사유를 기록한다.

### 데이터 병합 규칙 (정확성 우선)
- **가구:** `furniture`는 id → 항목 맵으로 두어 필드 단위로 병합한다. 같은 가구를 동시에 바꾸면 마지막 쓰기가 이기되 모든 클라이언트가 같은 상태로 수렴해야 한다.
- **방 polygon은 원자 단위:** 꼭짓점 필드별 CRDT 병합은 위상 불변식을 깰 수 있다. **단순히 각 클라이언트에서 잘못된 원격 변경을 버리면 서로 다른 상태로 영구 분기할 수 있으므로** 이 설계만으로 동시 편집 수렴을 보장하지 않는다. S6에서만 **동일한 서버/외부 호스티드 서비스가 직렬화하는 방 버전(`revision` CAS) 또는 만료/펜싱 토큰이 있는 단일 작성자 권한**을 도입해 검증된 polygon 전체를 원자적으로 승인·발행하도록 한다. 충돌 시 사용자에게 최신 방을 재조회·재적용하게 한다. 이를 보장할 제공자를 구할 수 없다면 S6을 실험 단계로 유지하고 출시하지 않는다.
- **원격 변경도 동일한 Zod·정규화 검증을 통과해야 화면에 반영**한다. 실패는 공급자 승인 단계에서 원자적으로 거부하고 공통 최신 snapshot을 재조회한다. 클라이언트별 필터링만으로 공유 문서 수렴을 보장한다고 주장하지 않는다.
- 방이 바뀌어 가구가 무효가 되는 것은 기존 철학대로 **삭제하지 않고 파생 경고**로 표시한다(동시 편집에서도 동일).
- **프리뷰는 공유 문서에 쓰지 않는다.** 드래그 중 ghost·커서·선택은 presence(awareness)로만 전파하고, 커밋만 문서에 기록한다.
- **Undo/Redo:** 가구 필드의 사용자별 변경은 CRDT origin 기반으로 되돌리되 다른 사용자의 값을 덮지 않는지 검증한다. 방 polygon은 서버 승인 revision이 여전히 본인 커밋 그대로일 때만 역변경 CAS를 시도한다. 타인이 이후 방을 수정했다면 자동 Undo로 덮지 않고 충돌 안내/재적용 선택을 제공한다. 되돌릴 대상이 삭제됐다면 안전하게 중단한다. 정상 편집 기록의 50단계 목표는 유지한다.

### 세션·저장
- 방 id는 추측 불가한 128bit 랜덤 값이며 링크(`#room=<id>`)를 아는 사람은 누구나 편집할 수 있다. 이를 공유 전에 사용자에게 고지한다. 읽기 전용 링크는 선택 구현이다.
- 사용자 식별은 임의 닉네임·색상뿐이다. 이메일·실명 등 개인정보를 수집하지 않는다.
- 입장 시 로컬 자동 저장본과 공유 문서가 다르면 **공유 문서를 우선**하되 덮어쓰기 전에 로컬 JSON 백업을 제안한다. 협업 중에도 각 클라이언트의 로컬 자동 저장은 유지한다.
- 연결 상태(연결됨/재연결 중/오프라인)를 `aria-live`로 안내하고, 오프라인 가구 필드 변경은 재연결 시 CRDT 병합 후 검증한다. **오프라인 방 polygon 편집은 기준 revision이 원격과 동일할 때만 CAS로 적용**하고, 충돌 시 사용자에게 최신 방을 보여 주고 재편집하도록 하며 임의로 덮어쓰지 않는다. 참가자 수는 8명, 문서 크기는 §3.2의 2MiB 한도를 따른다.
- 3D 보기는 읽기 전용이므로 “다른 사용자 카메라 따라가기”는 선택 기능이다.

### 협업 UX (Figma식 커서·채팅)
- **타인 커서:** 참가자마다 색상과 닉네임 이름표가 달린 커서를 캔버스에 표시한다. 좌표는 화면 px가 아니라 **world(mm)** 로 전송해, 상대방의 줌·팬이 달라도 같은 지점에 보이게 한다. 전송은 30~60ms로 throttle하고, 가만히 있으면 몇 초 뒤 흐려지며, 캔버스 밖이면 숨긴다.
- **타인 선택·작업 표시:** 타인이 선택한 가구는 그 사용자의 색 윤곽선과 이름표로, 드래그 중인 ghost는 반투명으로 표시한다(모두 presence 전용, 문서에 쓰지 않음).
- **참가자 목록:** 상단바에 아바타(닉네임 첫 글자+색)와 인원수를 표시하고, 클릭하면 해당 사용자의 위치로 화면을 이동한다(선택 기능).
- **커서 채팅:** `/` 키를 누르면 커서 옆에 입력창이 열리고, 보낸 말풍선은 몇 초 뒤 사라진다. 휘발성이며 저장하지 않는다.
- **채팅 패널:** 우측 패널의 “채팅” 탭. 텍스트만 지원하고 메시지는 500자, 전송은 초당 2건으로 제한한다. 세션 중에만 유지하고 입장 이후 메시지만 보이며 프로젝트 JSON·자동 저장에 넣지 않는다. 메시지는 React 텍스트 노드로만 출력하고(`innerHTML` 금지) 링크 자동 변환은 하지 않는다. 새 메시지는 `aria-live="polite"`로 알린다.
- 채팅과 커서 위치는 링크를 가진 모든 참가자에게 보인다는 점을 입장 시 고지한다. `/` 단축키는 §7 FR-023의 입력창 포커스 규칙을 따르고 레지스트리에 등록한다.
- 위치 고정 코멘트 핀(Figma 코멘트)은 P1이며 S6 범위가 아니다.

### 테스트
- 네트워크 없이 두 개의 인메모리 문서를 연결해 수렴·검증·Undo 규칙을 단위 테스트한다.
- Playwright로 브라우저 컨텍스트 2개를 열어 E2E를 수행한다. 지연 시간은 **측정값만 기록**하고 목표 달성을 단정하지 않는다.

### 16.2 세션 재개와 단계 게이트 (S0~S5 필수)

- 기존 저장소가 있다면 먼저 `git status`, branch, package scripts, 현재 테스트/빌드 상태와 완성 기능을 읽는다. 사용자 파일·기존 변경을 임의 삭제하거나 강제 reset하지 않는다. 새 작업은 가능하면 별도 브랜치에서 수행한다.
- 각 S단계는 **동작 가능한 파일**과 테스트를 남기고 `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`를 실제 실행한다. 필요한 E2E가 있다면 `npm run test:e2e`도 실행한다. 오류가 있으면 해당 단계에서 수정 후 재실행하며 실패한 상태로 다음 단계 완료를 선언하지 않는다.
- `PROGRESS.md`(세션 간 인계 장부)에는 단계별 `상태(미착수/진행/게이트통과) | 마지막 통과 명령과 종료코드 | AC 상태 | 다음 할 일 1~3개` 표와, 각 P0 요구사항 id의 `미착수/진행 중/코드 구현/검증 통과/차단`, 관련 파일, 테스트 로그/날짜, 실패 원인, 차기 작업을 기록한다. 기존 저장소에 `IMPLEMENTATION_STATUS.md`가 있으면 그 파일을 같은 용도로 이어 쓴다. `TEST_REPORT.md`에는 AC별 `통과/실패/미실행/환경상 불가`와 실제 명령의 종료 코드/증거를 쓴다. `DECISIONS.md`에는 정책과 대안을 남긴다. 이 셋과 `git log`를 기준으로 다른 에이전트 세션에서 재개한다.
- 레포에 push/Pages 설정 권한이 없다면 원격 배포를 성공으로 표시하지 않고 `배포 코드 준비/로컬 빌드 통과/원격 미검증`을 구분한다. 브라우저 E2E 실행 장치가 없다면 기하 unit 성공으로 E2E 통과를 대체하지 않는다.

### 16.3 사용자 여정 기반 UX 실패 방지 (P0)

- **A 원룸:** 새 방 → 침대·책상 추가 → 크기 수정 → 가구 겹침 오류 원인·겹친 상대가 표시됨 → 유효 위치로 이동 → 3D. `가구 선택` 또는 `수정`을 한 번에 발견할 수 있도록 카탈로그 클릭 추가, 편집기 툴팁, 우측 패널을 동시에 제공한다.
- **B ㄱ·ㄷ:** 예제 불러오기와 벽 중간 홈 생성은 **서로 다른 명령**이다. 프리셋은 전체 도형 교체 확인을 거치고, 홈 생성은 벽+시작+폭+깊이를 입력한다. 네 모서리만 포함되는 가구라도 홈 위를 가로지르면 구체적으로 `방 바닥 밖 영역을 가로지릅니다`를 표시한다.
- **C 구매:** 가구 크기를 1mm 단위로 숫자 입력 가능하게 하고 실측 도면 최단 이격을 보여 주되 제품 크기 예시·문틀/이동 동선 제외를 명시한다. 사용자가 경고를 해소할 수 있도록 양수 겹침과 높이 초과를 구분한다.
- **D 재개:** 자동저장 상태/마지막 저장 시각을 표시, 새로고침 시 확인 가능한 최신 프로젝트를 복구, 실패 시 JSON 백업·손상 데이터 보호·중복 탭 경고. 확인 없이 새 프로젝트로 덮지 않는다.
- 모든 실패는 한국어 텍스트+보조 아이콘으로 표시, aria-live는 과도한 드래그 프레임마다 말하지 않고 커밋·오류 변경 시에만 사용한다. 터치 HTML DnD가 안 되는 환경은 클릭 추가/숫자 편집을 정식 대안으로 제공한다.

### 17.1 필수 기하 unit test 고정값
- Rectangle: 4200×3400 = 14,280,000mm².
- L형: 12,360,000mm²; U형: 13,080,000mm².
- 위에서 함몰: -400,000mm² / 돌출: +600,000mm². 상단 벽 바깥 +200mm: 15,120,000mm²(bbox 4200×3600).
- `offsetMm` 부호: +는 `nOut`(면적 증가), −는 `nIn`. 함몰 안쪽 벽 +d → 홈 소멸·병합.
- 사선·0길이·중복점·자가교차·T자 접촉·빈 도형 거부.
- 벽 이동 ±값으로 polygon 직각·면적·연결 유지.
- 정방향 법선: 상단 벽 `(0,0)→(4200,0)` 기준 실내=(0,+1), 외부=(0,-1).
- 가구 1500×2000×500 중심(2100,1700), 90° => footprint 2000×1500.
- 가구 rect 접촉은 허용; 1mm 깊이의 양의 교차는 실패.
- ㄷ자 홈 점유(양끝 모서리가 방 안인 가구도) 실패.
- -좌표와 `.5` 경계(가구 중심 0.5mm 배수, 홀수 W/D에서도 정수 모서리), 100mm 스냅 후 mm 저장, 줌/팬 역변환.
- 가구 높이 > 실내 높이 거부. 기존 invalid 가구는 방 바꾸고 복구 가능.
- 2D world x/y → 3D x/z `mm/1000` 일치; 위쪽을 향한 floor normal.

### 17.2 통합/E2E 최소 구성
1. 신규 프로젝트 생성 → 방 수치 변경 → 벽/요철 생성 → 프리셋 예제.
2. 카탈로그 클릭 추가 및 실제 HTML→Stage 드래그 드롭(줌/팬 포함), 이동/회전/리사이즈/삭제/Undo.
3. 충돌 오류를 실제 화면에서 확인하고 무효 프로젝트 변경이 저장되지 않음.
4. 3D 탭 전환·카메라·WebGL 대체 화면 확인.
5. 자동 저장/새로고침/JSON 파일 roundtrip, 잘못된 파일 거부.
6. production preview 또는 Pages와 같은 `/<REPO>/` 조건에서 JS/CSS·3D 로딩과 주요 콘솔 오류 검사.

### 17.3 테스트 결과의 증거
- 각 단계에서 **실제로 실행한** `npm` 명령, 종료 코드/테스트 통과 수/실패 내용 제시. 명령 실행하지 않았으면 `미실행`이라고 표시.
- 브라우저 E2E/Playwright 미설치 환경에서 UI를 직접 검증하지 못했다면 사실대로 기록하고, 수동 검증 절차와 제약을 제시.
- 원격 Pages 주소에 접속하지 않았다면 `원격 배포 미검증`.
- 기능 스크린샷만으로 충돌·실측 정확성이 검증됐다고 말하지 않는다.

### 22.1 데이터·상태·명령 API 계약

```ts
type CommandResult =
  | { ok: true; kind: 'Committed'; project: ProjectDataV2; affectedIds: string[] }
  | { ok: true; kind: 'NoChange' }
  | { ok: false; kind: 'Invalid'; issues: Array<{ code: string; message: string; targetId?: string }> };

type EditorUIState = {
  tool: 'select'|'wallMove'|'indent'|'protrude'|'furniture';
  selected: { kind: 'room'|'wall'|'furniture'; id: string } | null;
  viewport: { zoomPxPerMm: number; panCssPx: { x: number; y: number } };
  draft: null | { kind: 'wallMove'|'notch'|'catalogDnD'|'furnitureMove'|'resize'; payload: unknown };
  modal: string | null;
  save: { status: 'clean'|'pending'|'saving'|'saved'|'failed'|'conflict'; lastSavedAt?: string };
};
```

`ProjectDataV2`만 영속 JSON에 넣는다. `EditorUIState`, history past/future, 계산된 warnings·mesh, UI settings의 wheel 방식은 프로젝트 JSON에서 제외한다. 다만 `ProjectDataV2.settings` 안의 grid/snap은 JSON에 **포함**하고 Undo에서 제외한다. 임시 draft는 메모리에만 둔다. 가구 `locked`는 P0에 넣지 않으며 선택 state 역시 JSON에 넣지 않는다.

### 22.2 요구사항 간 우선순위와 데이터 범위

- `P0 = S0~S5 완주`이고 단계는 작업 순서일 뿐 배포 수준의 기능 필터가 아니다. S6 협업은 사용자가 나중에 요청할 때만 실행하며 **현재 MVP 성공 기준에 포함하지 않는다**.
- 원본 UI 동작·수치 예제·AC를 적용하되 **구현 정확도를 위해 v3에서 추가된 정밀도·검증·상태 불변식이 같은 절의 해석 기준**이다. 특히 §3.3, §3.5, §8의 배치 판정, §9.1의 외벽 메시, §12의 import·autosave는 원자적으로 구현해야 한다.
- 제품은 배치 **시뮬레이터**이며 시공 가능성·반입 가능성·안전 법규 판단 도구가 아니다. 실측/실제품 치수·설치 여유를 사용자가 재확인해야 한다.
