# Dependency audit — 2026-11-02

`npm audit --json` reports **10 moderate package entries**, all in the development lint dependency tree, tracing to a single advisory: [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249), minimatch glob-parts amplification (denial of service), affected `<11.0.1`. The ten entries are `minimatch`, `eslint`, `@eslint/config-array`, `@eslint-community/eslint-utils`, `typescript-eslint`, `@typescript-eslint/eslint-plugin`, `@typescript-eslint/parser`, `@typescript-eslint/type-utils`, `@typescript-eslint/typescript-estree`, and `@typescript-eslint/utils`. These are propagated package entries, not ten distinct underlying advisories. Installed minimatch is 10.2.6. `npm audit --omit=dev --json` reports **zero vulnerabilities**. This does not mean application dependencies can never have unrelated vulnerabilities; it is this audit's current result.

Registry checks: minimatch **11.0.4** is the current stable release and requires Node 20 or >=22; this workspace runs Node 22.15.0. ESLint 10.14.0 declares minimatch `^10.2.6`, `@eslint/config-array` 0.23.5 declares `^10.2.4`, and `@typescript-eslint/typescript-estree` 8.72.1 declares `^10.2.2`. `typescript-eslint` 8.72.1 accepts ESLint `^8.57 || ^9 || ^10` and TypeScript `>=4.8.4 <6.1`. Consequently, a forced minimatch 11 override is outside all three consumers' declared ranges, even though its engine and dual ESM/CJS exports fit this Node version. The audit's proposed ESLint 4 downgrade is not a sensible automatic fix for this modern TypeScript setup.

Safest compatible path: keep the allowlisted direct toolchain and update ESLint/typescript-eslint once their stable releases consume a patched minimatch within their declared ranges, then regenerate the lockfile and run audit, lint, typecheck, unit and browser tests. If immediate mitigation is needed, evaluate an npm override to 11.0.4 in an isolated branch, document the unsupported major override, verify all three dependency paths with `npm ls minimatch`, and run the same full gates plus lint against representative file patterns. The override is a transitive pin, not a new direct runtime dependency; it still needs a conscious compatibility decision. This investigation changed neither package manifest nor lockfile.

The observed build has a **654 KB uncompressed single JS asset for the whole application**, not a measured 654 KB Konva-only chunk. The current `react-konva` entry imports full `konva`. A targeted size experiment is to import `react-konva/lib/ReactKonvaCore` and explicitly register only `konva/lib/shapes/Line` and `konva/lib/shapes/Text` (plus any later shapes used), then compare production build sizes and run browser interaction tests. Lazy-loading the editor can separate/defer the editor chunk but does not itself reduce its bytes; it should include a useful loading fallback and be measured. Do not raise Vite's chunk warning threshold to mask the result.
